# 운영

MINT를 설치해 돌리는 운영자가 반복해서 하는 일을 화면과 명령에 맞춰 적는다. 항목마다 자세한 규칙은 연결한 문서에 있고, MINT가 보장하지 않는 것은 [보장과 한계](보장과-한계.md)에만 적는다. 명령은 `mint-litellm`이며 배포 묶음에서는 `./mint.sh cli <명령>`으로 실행한다. 화면은 관리자 콘솔(기본 `MINT_CONSOLE_PORT`, HTTPS)의 메뉴 이름이다.

## 매일 보는 곳

| 할 일 | 화면 | 명령 |
| --- | --- | --- |
| 지금 기다리는 일 확인 | 「개요」 | `./mint.sh status`(토큰이 없으면 `mint-litellm doctor`) |
| 열린 경보 처리 | 「경보」 | `alert list --status open`, `alert ack <경보>`, `alert resolve <경보>` |
| 승인 대기와 만료 임박 | 「승인 대기열」 | `approve ...`, `revoke <승인>` |
| 호출별 승인 요청 | 「호출별 승인」 | `call-approval approve <요청>`, `call-approval reject <요청>` |
| 신청 결정 | 「신청·수용검증」 | `intake list --status <상태>`, `intake approve <신청>` |

식별자는 끝 8자리만 써도 한 건으로 정해지면 찾아 준다.

## 조직 연결 제안

콘솔 「운영자·조직」의 「조직 연결 제안」에 규칙별로 제안이 쌓인다. 관리자가 항목마다 「적용」 또는 「무시」를 누르거나 규칙 하나의 제안을 한꺼번에 적용한다. 적용 전에는 아무것도 묶이지 않는다. 명령줄은 `org suggest`, `org suggest apply`, `org domain set`을 쓴다.

## 승인과 재확인

- 새 서버: 「신청·수용검증」에서 신청을 열어 검사 결과를 보고 승인하거나 거절한다(`intake approve`, `intake reject`). 신청자와 같은 사용자는 승인할 수 없다.
- 승인은 90일(`MINT_RECERT_DAYS`)마다 「승인 대기열」의 「승인 내역」에서 「재확인」한다. 요청 뒤 14일(`MINT_RECERT_GRACE_DAYS`) 안에 확인이 없으면 승인이 보류되어 호출이 `APPROVAL_RECERT_REQUIRED`로 막힌다. 경보 `approval_recert_due`·`approval_recert_held`가 알려 준다.
- 만료 7일 전 경보 `approval_expiring`이 열린다. 계약과 위험 등급이 그대로인 승인은 「승인 대기열」의 「일괄 갱신」으로 같은 범위·길이로 새로 만든다.
- 계약이 바뀌어 막힌 서버는 「계약 변경」에서 후보를 확인하고 재승인한다(`contract reapprove <서버> --intake <신청> --tool-contract <후보>`).

## 호출별 승인 요청

승인이 없어 막힌 호출은 같은 주체·서버·도구·인자의 대기 요청이 없을 때 호출별 승인 요청(24시간)을 대기 상태로 열고 경보 `call_approval_requested`로 알린다. 승인은 사람이 한다. 「호출별 승인」에서 승인·거절하거나 `call-approval approve`·`call-approval reject`를 쓴다. 호출 주체와 같은 사용자는 승인할 수 없다. 인자 지문은 [CLI](CLI.md)의 「호출별 승인의 인자 지문」을 본다.

「호출별 승인」 화면의 각 요청에는 무엇을 승인하는지가 함께 보인다. 서버·도구, 대상·동작(있으면), 호출 인자(최상위 이름별로 비밀·개인정보를 가리고 200자까지 자른 값), 요청한 주체와 요청 시각이다. 인자 원문은 저장하지도 보이지도 않는다. 거절할 때는 사유를 적을 수 있고(`call-approval reject <요청> --reason ...`) 사유는 같은 호출을 다시 보낸 요청자의 오류 응답(`denial_reason`)과 화면에 그대로 전해진다.

거절은 그 요청 1건에 한정된다. 거절된 요청과 같은 호출(같은 주체·서버·도구·인자)을 `MINT_CALL_DENIAL_MINUTES`(기본 30분) 안에 다시 보내면 새 요청도 경보도 열지 않고 `MINT-CALL-APPROVAL-DENIED`로 바로 거절한다. 인자가 하나라도 다르면 평소처럼 새 요청이 열린다. 시간이 지나면 거절 기록은 조회에서 빠지므로 쌓이지 않으며, 영구히 막으려면 도구를 비활성화한다. 승인이 쓰이지 않고 만료된 뒤 같은 호출을 다시 보내면 새 요청이 열리고 오류 응답에 `previous_expired`가 담긴다. 승인된 호출은 다음 같은 호출에서 기존대로 승인을 소비하고 진행한다. 요청자별 알림 채널은 없으므로 결과는 이렇게 다음 호출의 응답으로만 전달된다.

## 도입 신청 초안

LiteLLM에 제출된 서버는 작업 실행기가 신청으로 만들고, 제공자(서버 주소의 호스트)·허용 자원(도구 목록)·책임자(제출자)를 미리 채운 뒤 경보 `intake_pending`으로 알린다. 운영자는 목적·자료 등급·종료 준비도·반환 조건을 채워 신청을 완성한다(콘솔 신청 화면 또는 `intake create <서버> --purpose ... --data-grade ...`). 서비스 계정이 제출해 신청자가 비어 있으면 `intake assign <신청> --requester <사용자>`로 사람을 지정한다. 입력과 신청자가 갖춰지면 검사가 시작된다.

## 경보와 웹훅

「경보」 화면은 열린 경보를 심각한 순서로 보이고 상태·심각도·종류·서버로 거른다. 경보를 열어 상세와 관련 화면 링크를 보고 「확인함」으로 처리한다(`alert ack`). 원인이 사라지면 `alert resolve`로 닫는다. 메뉴의 표지는 확인하지 않은 높음·심각 경보 수이다.

웹훅은 `MINT_WEBHOOK_URLS`(https 주소 목록)와 서명 키 `MINT_WEBHOOK_HMAC_KEY`를 설정하면 새 경보마다 전송한다. 본문은 `summary`(요지), `action`(담당자가 할 조치), `kind`, `severity`, `subject`, `count`, `first_at`, `last_at`, `console_url`을 담고 헤더 `X-MINT-Signature`·`X-MINT-Delivery`로 서명과 전송 식별자를 보낸다. 서명 검증과 재시도 규칙은 [CLI](CLI.md)의 「경보와 웹훅」을 본다.

### 대량 추출 경보

작업 `bulk_extraction_scan`은 1분마다 호출한 쪽과 서버별로 최근 15분에 받아 간 결과의 바이트 수와 항목 수를 지난 7일 평균과 견준다. 평균의 5배 이상이면서 5 MiB 또는 2000항목 이상이면 경보 `bulk_extraction`(높음)이 열리고, 평소 수준으로 돌아오면 닫힌다. 열려 있는 동안 다시 알리지 않는다. 서버 전체 합계도 같은 규칙으로 보며, 이 경보에는 호출한 쪽이 없다. 호출한 쪽의 식별자는 경보 상세에만 나오고 지표 라벨에는 쓰지 않는다. 기준은 `MINT_BULK_*` 환경 변수로 바꾼다.

`MINT_BULK_EXTRACTION_ACTION=hold`로 두면 경보가 새로 열릴 때 그 호출한 쪽의 해당 서버 호출을 막는 거부가 함께 만들어진다. 막힌 호출은 `DENIED`로 거부된다. 확인한 뒤 콘솔 「거부」 화면에서 해제하면 다시 호출할 수 있다. 경보가 닫혀도 거부는 해제되지 않는다.

## 증빙 첨부

사람이 확인하는 정책은 증빙(요약, 문서 위치, 해시, 유효 기한)을 대상에 붙여야 통과한다. 콘솔은 신청 화면과 서버 상세에서 붙이고, 명령은 다음과 같다.

```
mint-litellm evidence show <intake|server|relation> <대상>
mint-litellm evidence attach <종류> <대상> --summary <요약> [--ref <문서 위치>] [--sha256 <해시>] [--valid-until <기한>]
```

종류별 대상·필수 자리·기본 유효 기간은 [CLI](CLI.md)의 「증빙 첨부와 이용 관계 종료 완료」 표를 본다. 증빙이 없거나 만료됐거나 7일 안에 끝나면 경보 `evidence_missing`·`evidence_expiring`이 열린다.

## 여러 인스턴스의 일치

같은 DB에서 같은 서버를 계약 관리하는 인스턴스가 둘 이상이면 관측 주기마다 승인 계약과 보안 설정(가드레일 모드, 활성 정책 묶음)을 비교한다. 다르면 경보 `instance_mismatch`가 바로 열리고, 차이가 `MINT_INSTANCE_MISMATCH_GRACE_SECONDS`(기본 900초)를 넘게 이어지면 어긋난 인스턴스에서 그 서버의 호출이 `CONTRACT_DRIFT_instance_mismatch`로 막힌다. 정책 묶음 활성화나 설정 변경은 인스턴스마다 이 시간 안에 끝낸다. 서버 상세에 사유가 보인다. 풀려면 인스턴스끼리 계약·설정을 맞추거나, 의도한 차이면 admin이 서버 상세의 증빙 「인스턴스 간 불일치 예외」를 붙인다(`evidence attach instance_exception <서버>`, 30일 이하). 다음 관측 주기에 반영된다. 인스턴스가 하나뿐이면 아무 영향이 없다. 범위와 한계는 [보장과 한계](보장과-한계.md)를 본다.

## 서버 폐기와 이용 관계 종료

- 서버 폐기: `server terminate <서버>`. 호출은 즉시 차단되고 작업 실행기가 LiteLLM에 저장된 사용자별 OAuth2·API 키 자격을 지운 뒤 목록을 다시 읽어 비었을 때만 폐기됨으로 닫는다. 서버 계정·문서 공유 권한을 회수한 뒤 `evidence attach access_revocation <서버> --summary <사유>`를 붙이면 마무리가 이어진다. 확인하지 못한 항목은 [보장과 한계](보장과-한계.md)의 9-1을 본다.
- 일시 중지와 복귀: `server suspend <서버>`, `server resume <서버>`. LiteLLM에서 서버를 지우기 전에는 먼저 중지한다(순서는 [CLI](CLI.md)의 「서버를 LiteLLM에서 삭제하는 순서」).
- 이용 관계 종료: `relation terminate <관계>`로 활성 승인을 철회하고, 자료 삭제·반환 증빙(`deletion_proof`)을 붙인 뒤 `relation finish <관계>`로 닫는다.

## 정책 시험 적용

새 정책 판본은 먼저 시험 적용한다. 호출의 판정은 바뀌지 않고, 활성 판본과 시험 판본의 결과가 다른 호출만 센다.

1. `docker compose --profile shadow up -d opa-shadow`로 시험용 정책 엔진을 띄우고 LiteLLM 컨테이너에 `MINT_SHADOW_OPA_URL=http://opa-shadow:8181`을 준다.
2. `mint-litellm policy shadow <판본>`.
3. 「정책·관측 설정」의 「정책 시험 적용」에서 평가한 호출 수와 「허용에서 차단」·「차단에서 허용」 호출 목록을 본다(`policy status`도 같다).
4. 괜찮으면 같은 화면의 「적용」(또는 `policy activate <판본>`), 아니면 「취소」(`policy shadow-cancel`).

## 지표

`GET /api/v1/metrics`(콘솔, `Authorization: Bearer <운영자 토큰>`)가 Prometheus 텍스트 형식으로 판정 수, 판정 시간, 대기 작업, 서버별 마지막 관측 경과, 열린 경보를 낸다. 지표 목록은 [설정](설정.md)의 「지표」를 본다. 판정 수·결과 수·판정 시간은 작업 `metric_rollup`이 1분마다 쌓는 누적 건수에서 읽으므로 작업 실행기가 멈추면 롤업 뒤의 사건이 모두 꼬리로 남아 수집이 느려진다(값은 그대로 맞다). 콘솔 개요의 「집행 상태」에는 복제본마다 LiteLLM 판본과 보장 등급이 보이며, 검증되지 않은 판본이나 등급 B 이하는 경고로 표시된다. 대기 작업의 가장 오래된 대기 시간과 `mint_alerts_open`에 경고 기준을 두면 작업 실행기 정체를 빨리 안다.

## 단말 설치 묶음의 보고와 키 갱신

직원은 콘솔 직원 화면의 「단말 설치」에서 묶음을 내려받는다. 설치한 단말은 6시간마다 설치 상태를 보고하고, 만료 14일 안의 정상 보고가 키 기간을 자동으로 늘린다(기본 90일, `MINT_ENDPOINT_KEY_DAYS`). 운영자는 「단말 설치」에서 사용자별 설치 상태·마지막 보고를 본다.

- 경보 `endpoint_egress_refused`: 허용 호스트 목록이 있는 서버의 접속이 목록 밖이라 거절되었다. 단말에서 서버 실행기 출력의 `mint-egress refuse` 줄로 어떤 호스트인지 보고, 필요한 호스트면 계약에 더해 다시 승인하고 아니면 서버를 중지한다. 프로세스가 끝나면 닫힌다.
- 경보 `endpoint_egress_unfiltered`: Windows 단말에서 `network: hosts`를 선언한 서버가 호스트 제한 없이 실행 중이다. AppContainer는 호스트별 거름을 할 수 없어 인터넷 클라이언트 기능만 주고 서버는 인터넷 전체에 접속할 수 있다. 호스트 제한이 필요한 서버는 Linux 단말에서 실행하거나 `network: none`으로 다시 승인한다. 관리자 계정 Windows 보고기는 계약을 모르므로 제어 평면이 계약으로 판정한다: 승인 계약이 `network: hosts`인 서버가 `appcontainer`로 보고되면 보고에 플래그가 없어도 이 경보가 열린다.
- 경보 `endpoint_unsandboxed`: 관리형 단말에서 로컬 서버가 격리 없이 실행 중이다. 단말에 `bubblewrap`을 설치하고 사용자 이름공간이 허용되는지 확인한 뒤 서버를 다시 시작한다. 관리형 설치는 격리할 수 없으면 서버를 시작하지 않으므로(종료 코드 126) 이 경보는 `MINT_ENDPOINT_ALLOW_UNSANDBOXED`로 받은 묶음이 격리 없이 시작했을 때 열린다. Windows 단말은 AppContainer로 격리하며(Windows 8 이상), 서버를 시작할 때마다 사용자 프로필 아래에 임시 AppContainer를 만들고 선언한 경로에 접근 권한을 더했다가 서버가 끝나면 지운다(실행기가 비정상 종료해 남은 권한은 다음 시작 때 정리된다). 서버가 크면 이 준비에 수 초가 걸릴 수 있다. 관리자 계정 Windows 보고기는 사용자 프로필의 실행 기록 대신 서버 프로세스의 토큰으로 격리 상태를 판정하므로 관리형 Windows에서도 이 경보가 열린다(토큰을 읽지 못하면 「격리 미지원」). 「단말 설치」 화면의 「서버 격리」 열에서 서버별 격리 상태(격리됨·격리 없음·격리 미지원)를 본다.
- 로컬 서버의 네트워크는 실행 계약의 선언으로 정한다. `server register-local --network none`이면 격리가 네트워크를 막고, `--allow-host api.example.com` (반복 가능, `*.example.com`·`호스트:포트` 가능)을 주면 `network: hosts`로 그 호스트만 서버 실행기의 중계를 거쳐 나갈 수 있으며(Linux만. Windows는 호스트 제한이 집행되지 않고 경보 `endpoint_egress_unfiltered`가 열린다. 프록시 환경 변수를 무시하는 클라이언트는 닿지 못한다. 허용 목록이 늘어나면 네트워크 축 확대로 재승인을 받는다), 선언이 없거나 `any`이면 막지 않는다(콘솔 서버 상세에 「네트워크 미제한」으로 보인다). 등록할 때 계약에 주소나 패키지 실행기가 보이면 「이 계약은 네트워크를 쓸 것으로 보입니다」를 알려 준다.
- 경보 `endpoint_silent`: 보고가 `MINT_ENDPOINT_SILENT_HOURS`(기본 24) 넘게 끊겼다. 단말이 꺼져 있거나 묶음이 지워진 것이다. 보고가 다시 오면 닫힌다.
- 경보 `endpoint_key_expiring`: 만료 7일 안인데 갱신되지 못했다. 직원이 설치 묶음을 다시 내려받아 설치하면 정리된다.
- 만료된 키의 보고는 거부된다.
- 폐기·미승인 서버 정리: 보고 응답에는 MINT가 폐기·반려·미승인으로 보는 서버 이름 목록(`retired`)이 실린다. 관리형 설치의 보고기(Linux는 시스템 타이머, Windows는 SYSTEM 예약 작업)가 목록에 든 서버의 관리형 설정 항목과 묶음 실행기가 띄운 프로세스, 묶음이 등록한 자동 시작 항목을 지우고 곧바로 다시 보고한다. 지운 항목마다 사건 `endpoint_remediated`(이벤트 화면의 「단말 항목 자동 제거」)가 남고, `endpoint_stale_server`·`endpoint_stale_process`·`endpoint_stale_autostart` 경보는 다음 점검에서 닫힌다. 서버 실행기도 목록에 든 서버를 시작하지 않는다. 사용자 수준 설치와 사용자가 만든 항목은 건드리지 않고 경보만 남으며, 정리가 일어나려면 단말의 보고기가 돌아야 한다. 정리된 서버를 다시 승인하면 다음 보고 응답의 승인 서버 목록으로 관리형 설치가 스스로 되돌려 받는다(아래).
- 승인 서버 목록 반영: 보고 응답에는 MINT가 승인한 로컬 서버의 목록(`desired`: 서버 이름·실행 계약·계약 판본)도 실린다. 새로 승인했거나 계약이 바뀌었거나 정리된 뒤 다시 승인한 서버가 있으면 관리형 설치의 보고기가 계약 파일과 관리형 설정(Claude Code 관리형 MCP 목록, Codex 요구·서버 정의 파일과 Windows의 표식 구간)에 그 서버를 더하거나 갱신하고, 곧바로 다시 보고한다. 단말은 실행기 인자를 자기 설치 경로로 만들며, 판본이 계약 내용과 맞지 않는 항목은 버린다. 이 묶음이 쓴 계약 파일(기록한 해시와 같을 때만)과 이 묶음의 실행기로 시작하는 항목만 고치고, 같은 이름의 사용자 항목은 건드리지 않으며 지우는 일은 위의 폐기 서버 정리가 한다. 사용자 수준 설치는 파일을 고치지 않고 바뀐 서버 이름을 보고기 출력에 남길 뿐이라 묶음을 다시 내려받아 설치해야 반영된다.
- 단말 MCP 목록: 운영자 콘솔 「단말 설치」의 「단말 MCP 목록」은 단말의 Claude Code(`~/.claude.json`)·Codex(`~/.codex/config.toml`) 설정에서 MINT가 관리하지 않는 MCP 서버를 보여 준다. 설치마다 서버 이름·도구·전송 방식·실행 파일 이름이나 원격 호스트·처음과 마지막으로 본 시각·같은 항목을 보고한 단말 수가 나오고, 「신청 시작」은 이름·제공자·책임자를 채운 신청 입력 화면을 연다. 인자·환경 변수·헤더·URL의 사용자 정보와 경로·질의는 단말에서 읽지 않으며, `npx`·`uvx` 같은 실행기는 패키지 이름만 더한다. 해제된 키와 제거 보고의 설치는 목록에서 빠진다.

## 올리기와 백업

- 올리기: `./mint.sh upgrade` 뒤 [업그레이드](업그레이드.md)의 점검 목록을 순서대로 한다.
- 백업: `./mint.sh backup`. 되돌림 뒤의 확인은 `restore check`, `restore attest`([CLI](CLI.md)), 범위는 [보장과 한계](보장과-한계.md)의 11을 본다.
- 점검: `mint-litellm check`, `mint-litellm doctor`.
