# 보장과 한계

이 문서는 MINT가 보장하는 것과 보장하지 않는 것을 구분한다. 「집행됨」이라고 말할 수 있는 범위는 호출이 지나는 훅 경로와 기동 시 자가 점검이 증명하는 범위뿐이다. 그 밖의 경로는 아래에서 한계로 선언한다.

## 1. 보장하는 것

- **도구 호출 판정.** `tools/call`은 `/mcp`, `/mcp-rest/tools/call`, 응답·채팅 API의 자동 실행에서 LiteLLM의 사전 훅을 지나며, 판정은 이 훅 경로에서만 성립한다. 사전 훅을 지나지 않는 경로는 보장하지 않는다(아래 「`/mcp/proxy` 면」, 「판정이 보지 못하는 인자 변경」). 판정은 병렬로 도는 MINT 가드레일이 한다. LiteLLM은 병렬 가드레일을 순차 훅이 모두 끝난 뒤의 최종 인자로 돌리고 차단 예외가 나면 업스트림에 닿기 전에 요청을 거부한다. 판정하는 인자는 LiteLLM 전송부가 고르는 인자와 같다. 앞선 훅이 돌려준 수정본이 있으면 그것이고, 없으면 훅에 들어오기 전의 원래 인자이다. 사전 훅 데이터의 `mcp_arguments`가 원래 인자와 같다고 확인되지 않으면(앞선 순차 가드레일이 수정본 없이 이 값만 바꾼 경우) 판정하지 않고 `MINT-SCHEMA-ERROR`로 차단한다. 이 가드레일은 키·팀 메타데이터의 가드레일 제외 설정과 무관하게 판정한다. 가드레일이 도는 단계에서 서버·도구 이름이 없거나 호출 데이터가 객체가 아니면 판정하지 않고 `MINT-SCHEMA-ERROR`로 차단한다(REST 요청 본문 단계는 LiteLLM이 가드레일을 건너뛴다). 응답·실패 관측은 MINT 로거가 맡는다.
- **공급자 쪽 MCP 차단.** 모델 요청(`/v1/chat/completions`, `/v1/responses`, `/v1/messages`)과 패스스루 경로(`/anthropic/*`, `/openai_passthrough/*` 등)의 본문을 `pre_call` 단계에서 재귀로 훑는다. `extra_body`·`input`·`session` 등 어느 자리든 구조화된 `type: "mcp"` 객체나 비어 있지 않은 `mcp_servers`가 있으면 공급자가 승인되지 않은 서버를 직접 호출하게 되므로 `MINT-EXTERNAL-MCP-FORBIDDEN`(403)으로 막고 판정 사건(`operation: llm_request`)을 남긴다. 요청은 공급자에게 나가지 않는다. 예외는 최상위 `tools[]`의 `litellm_proxy` 형식 주소(`litellm_proxy`, `litellm_proxy/mcp/<이름>`)뿐이며 LiteLLM이 게이트웨이 경로로 실행하므로 도구 호출 판정을 지난다. 임의 호스트의 `/mcp/<이름>` 경로는 게이트웨이로 인정하지 않는다. 패스스루에는 LiteLLM의 내부 MCP 처리가 없으므로 게이트웨이 형식이라도 `type: "mcp"`를 모두 막는다. 문자열 `extra_body`는 JSON으로 풀어 같은 검사를 하고(LiteLLM이 풀어 공급자 요청에 합칠 수 있다), 문자열로 들어온 `tools`·`mcp_servers`·`session`은 지원하지 않는 형식으로 막는다. 메시지 본문 텍스트(`messages[].content`, 문자열 `input`, `input[].content[].text`)와 `metadata` 같은 다른 문자열은 풀지 않으므로 JSON 문자열을 붙여 넣은 정상 요청은 막히지 않는다. 깊이(24)·노드 수(10만)·`extra_body` JSON 크기(100만 자) 상한을 넘어 판정할 수 없는 본문도 막는다. 이 판정은 마스터 키·키 메타데이터의 가드레일 제외 설정과 무관하게 돌며, 판정 중 오류가 나면 통과시키지 않고 막는다. 사건에는 URL을 남기지 않고 항목의 종류(`tools`·`mcp_servers`·`unsupported`·`limit`)만 남긴다.
- **실시간 경로 거부.** `/v1/realtime`(WebSocket), `/v1/realtime/client_secrets`, `/v1/realtime/calls`, `/v1/realtime/transcription_sessions`는 연결 뒤 `session.update`로 도구를 더할 수 있고 그 메시지는 사전 훅을 지나지 않아 MINT가 볼 수 없다. 그래서 이 경로의 요청은 기본으로 `pre_call` 단계에서 `MINT-REALTIME-FORBIDDEN`(403)으로 막고 판정 사건을 남긴다. 환경 변수 `MINT_ALLOW_REALTIME=true`로 운영자가 명시해야 허용하며, 허용해도 세션 생성 본문의 외부 MCP는 막지만 연결 뒤 `session.update`로 더하는 도구는 판정하지 못한다. LiteLLM의 OpenAI WebSocket 패스스루(`general_settings.enable_openai_websocket_passthrough`, 별도 활성화, `/openai/*`·`/openai_passthrough/*` WebSocket)는 사전 훅 자체를 거치지 않으므로, 이 설정이 켜져 있으면 `MINT_ALLOW_REALTIME=true`를 함께 명시하지 않는 한 자가 점검의 필수 설정 항목이 실패해 기동이 멈춘다. 허용하면 그 경로의 도구는 MINT가 판정하지 못한다.
- **모델 생성 코드 실행 거부.** LiteLLM 스킬 훅(`proxy/hooks/litellm_skills/main.py`, `PROXY_HOOKS`에 있어 프록시가 항상 올린다)은 요청의 `container.skills`를 보고 `litellm_code_execution` 도구를 주입한 뒤, 응답의 그 도구 호출을 llm-sandbox Docker 샌드박스에서 직접 실행한다(`llms/litellm_proxy/skills/code_execution.py`). 끄는 설정은 없고, 전제는 llm-sandbox 설치·Docker·DB의 스킬(`litellm_skill_` 접두)이다. 설정의 `code_interpreter_interception` 콜백을 켜면 `tools[].type=code_interpreter`도 같은 방식으로 가로채 실행한다(`integrations/code_interpreter_interception/handler.py`). 둘 다 MCP가 아니라서 MCP 훅을 지나지 않는다. MINT는 `pre_call` 단계에서 `container`, `code_interpreter`·`code_execution*` 도구, `litellm_code_execution` 도구와 그 활성 표지(스킬 훅이 `container`를 지운 뒤에도 남는 흔적)를 `MINT-CODE-EXECUTION-FORBIDDEN`(403)으로 막는다. `MINT_ALLOW_CODE_EXECUTION=true`로 운영자가 명시해야 허용한다. 자가 점검은 `code_interpreter_interception`이 켜져 있으면 허용을 명시하지 않는 한 필수 설정 항목을 실패시킨다. llm-sandbox는 공식 이미지에 늘 들어 있어 기동을 막지 않고, 그 요청은 사전 단계에서 막힌다. 한계: 검사는 요청 본문의 최상위와 `extra_body`만 보고, 허용하면 실행되는 코드는 MINT가 판정하지 못한다. 공급자가 자기 쪽에서 실행하는 코드 도구도 같은 이름으로 막는다.
- **판정 불능이면 차단한다.** 데이터베이스나 정책 엔진을 쓸 수 없거나, 정책 판본이 일치하지 않거나, 출력이 정의 밖이면 호출은 업스트림으로 나가지 않는다.
- **감사할 수 없으면 허용하지 않는다.** 허용 경로에서 판정 사건을 먼저 기록하지 못하면 호출을 차단한다. 차단 경로의 기록 실패는 결과를 바꾸지 않고 로컬 버퍼에 남긴다.
- **명시적 부정 상태는 항상 차단한다.** 거부, 중지·종료된 서버, 종료 중인 이용 관계, 필수 동의의 부재·만료·철회, 철회·만료 이력만 남은 주체, 만료된 허용 목록 근거, 조직·배치 경계 밖, 익명 호출, 마스터 키 호출은 관측 모드에서도 차단한다.
- **플러그인 미적재를 허용하지 않는다.** 기동 후 자가 점검 8항목을 모두 통과하기 전에는 들어온 모든 MCP 호출을 차단하고, 점검에 실패하면 사건을 남기고 프록시 기동을 중단한다. 자가 점검은 워커 프로세스마다 한 번 실행한다. 이 보장은 플러그인이 적재된 경우에만 성립하며, 적재되지 않은 채 기동하는 구성은 LiteLLM이 막지 않는다.
- **본문 미저장.** MINT가 소유한 저장소(`mint` 스키마, 사건, 로컬 버퍼, MINT 로그)에는 도구 인자, 결과 본문, 의무 값을 저장하지 않는다. 지문, 정책 식별자, 의무 종류만 남긴다. 예외는 이용자 본인 확인 한 가지다. 정책이 본인 확인에 보여 줄 필드를 지정하면 그 필드의 값이 필드마다 256자까지 확인 요청 행에 저장되고(필드를 지정하지 않으면 인자 이름과 크기만), 확인·거절·취소·만료로 요청이 끝나는 같은 트랜잭션에서 지워진다. 끝나기 전까지는 데이터베이스와 그 시점의 백업에 남는다.
- **네임스페이스.** 모든 레코드는 배치와 조직 범위를 가지며, 다른 배치·조직의 승인과 거부는 후보에서 제외된다.

## 1-1. LiteLLM 판본과 보장 등급

기동할 때 MINT는 판본 번호가 아니라 설치된 LiteLLM에서 MINT가 쓰는 훅 지점(호출 판정 모드, 서버 해석, 결과 단계 가드레일과 로거 훅, 도구 목록 호출 형식, 이름 해석)이 있는지와 그 매개변수를 확인해 등급을 정한다. 현재 등급은 `mint status`가 보인다.

| 등급 | 갖춘 훅 | 성립하는 보장 | 기동 |
|---|---|---|---|
| A | 호출 판정, 결과 단계 가드레일, 도구 목록 훅, 이름 해석 | 이 문서의 모든 보장 | 가능 |
| B | 호출 판정, 결과 단계 가드레일. 도구 목록 훅이나 이름 해석 중 하나 이상 없음 | 호출 판정과 결과 검사. 목록 숨김은 LiteLLM 권한 동기화(`sync_reconcile`이 키·팀 권한을 쓴다)에만 기대고 목록 사건·목록 중복 제거가 없다 | 저하 운용을 켠 경우만 |
| C | 호출 판정만. 결과 단계 가드레일 없음 | B에서 잃는 것에 더해, 결과는 로거 훅으로 관측만 하고 마스킹·차단은 하지 못한다 | 저하 운용을 켠 경우만 |
| D | 호출 판정 지점 없음 | 없음 | 거부 |

B·C·D는 빠진 능력 이름을 밝히고 기동을 거부한다(기본). 운영자가 환경 변수 `MINT_ALLOW_DEGRADED_LITELLM=true`로 명시하면 B·C는 저하 운용으로 기동한다(D는 늘 거부). 저하 운용은 잃는 보장을 모두 드러낸다. 기동 로그에 한 줄씩 경고하고, 기동 점검 통과 사건(`enforcement_verified`)의 `degraded`에 남기고, `mint status`가 보장하지 않는 것과 집행이 약해지는 정책(B는 POL-O-02, C는 POL-E-04·POL-E-05·POL-E-16·POL-O-02)을 적는다. 등급 C에서는 결과 검사(비밀·개인정보 가리기, 결과 크기 상한, POL-E-04 지시문 표지)가 걸려도 결과를 막거나 가리지 못하고 그대로 전달된다. 걸린 건은 응답 사건에 `result_unenforced: true`로 남고 경보 `result_unenforced`(작업 `result_unenforced_scan`이 1분마다 최근 10분을 센다)가 열린다. 보장할 수 없는 기능을 켠 채 「집행됨」이라고 말하지 않기 위해서이다. 시험한 판본(1.106.6, 1.108.5)이 아닌 판본은 등급 A여도 기본으로 거부하며, 운영자가 환경 변수 `MINT_ALLOW_UNTESTED_LITELLM=true`로 명시하면 기동하고 `mint status`에 「검증되지 않은 판본」으로 표시하고 기동 로그에 경고를 남긴다. 이 허용은 감지된 능력의 존재와 매개변수만 확인한 것이므로 동작 보증이 아니다. 새 판본이 훅 모양을 바꾸면 호환 계약 시험(`tests/unit/compat/test_litellm_contract.py`)이 야간 워크플로에서 먼저 깨진다.

## 2. 철회 효력과 잔존 구간

승인 철회, 거부 생성, 서버 중지 등 집행에 영향을 주는 변경은 같은 트랜잭션에서 상태 세대를 올린다. 철회된 승인이 그 호출의 유일한 허용 근거였던 경우, 철회가 커밋된 뒤에 시작된 호출은 차단된다. 같은 주체 범위에 다른 유효 승인이 있으면 그 승인으로 허용되며, 주체를 모든 승인에서 끊으려면 철회와 함께 거부를 만든다(`revoke --deny`).

철회 전에 상태를 읽은 호출은 다음 구간에서 허용된 채 진행될 수 있다.

1. 상태 스냅숏을 읽은 시점부터 LiteLLM이 업스트림으로 전송하기까지의 구간(판정 예산 300ms 이내).
2. 읽기 복제본을 쓰는 경우의 복제 지연(기본은 프라이머리를 직접 조회한다).
3. 이미 전송된 호출. 전송된 호출은 취소하지 않는다.

응답 단계에서 상태 세대가 바뀐 것이 확인되면 선택된 승인·거부·관계의 현재 상태를 다시 읽어 `revoked_after_snapshot`을 사건에 기록한다. 세대를 읽을 수 없으면 값을 비우고 `revocation_check: unavailable`로 기록한다. 응답이 오지 않으면 `call_outcome_unknown` 사건을 남긴다.

LiteLLM에 남아 있는 권한은 호출을 허용하는 근거가 아니다. 호출 판정은 LiteLLM의 권한과 무관하게 MINT가 수행한다. 잔존 권한의 영향은 훅을 지나지 않는 경로에 한정된다.

## 3. 사건의 증거 위치와 중복

증거의 단위는 사건의 `source_key`이다. 최초 기록은 한 위치에서만 시도한다.

1. 데이터베이스
2. 데이터베이스를 쓸 수 없으면 로컬 버퍼(`/var/lib/mint/buffer`, 복제본별 명명 볼륨)
3. 버퍼에도 쓸 수 없으면 표준 오류의 구조화 로그(`evidence: stderr`). 이 경우 호출은 차단한다.

기록 결과가 불명인 경우(커밋 뒤 응답 유실, 버퍼 fsync 실패)에는 다음 위치에 다시 기록하므로 같은 `source_key`가 두 위치에 남을 수 있다. 버퍼 재적재 시 배치와 `source_key`의 유일 제약이 한 건으로 수렴시키며 중복 건수는 `buffer_replayed` 사건에 기록한다.

허용 판정 사건을 DB에 쓰다 결과가 불명이어서 호출을 막은 경우(`MINT-AUDIT-FAILURE`)에는 허용 사건이 이미 커밋되어 있을 수 있다. 이때 차단 사건은 같은 키가 아니라 같은 호출의 다음 시도(`<호출 식별자>:2`)로 남기고 본문의 `original_decision_ref`에 허용 사건의 참조를 담으므로, 재적재가 차단 사건을 중복으로 버리지 않는다. 같은 호출의 판정 사건이 여럿이면 시도 번호가 가장 큰 사건이 최종 집행이다. 호출자에게 돌려준 오류의 `reference`는 이 최종 사건을 가리킨다. 도구 목록 판정(`discovery_evaluated`)도 도구마다 같은 규칙을 따른다.

도구 목록 판정(`discovery_evaluated`)의 「보임」 통과 기록은 같은 키가 반복되면 다시 쓰지 않는다. 키는 주체(유형·식별자·키·팀·조직), 서버, 도구, 상태 세대, 설정 판본, 활성 정책 판본이며 유효 시간은 `MINT_LIST_DEDUP_SECONDS`(기본 하루)이다. 그래서 원장은 「누가 어떤 도구를 볼 수 있었는지」를 키가 처음 나타난 시각(그 상태 세대에서 처음 본 순간)과, 상태 세대·설정·정책이 바뀌어 다시 기록된 시각으로 보여 준다. 승인·거부·서버 변경은 상태 세대를 올리므로 보임이 바뀌면 새 기록이 남고, 숨김·차단·걸림은 줄이지 않는다. 호출 판정·승인·응답 사건은 줄이지 않는다. 중복 기억을 읽다 오류가 나면 사건을 쓰고, 기록이 저장되지 않으면 기억에 넣지 않는다.

판정 사건 본문은 2판(`v: 2`)으로 기록한다. 비어 있는 값과 기본값(`mode`가 enforce, `evaluated_decision`이 `enforced_action`과 같음), 모두 통과한 `stages`(걸림·정지·그 밖의 건너뜀만 남김), 주체의 `provenance`·`org_source`·`instance_id`, 활성 판본에서 찾을 수 있는 `bundle_sha256`, 값이 없다는 사실만 되풀이하는 `missing_reasons`를 적지 않는다. 이미 기록된 1판 행은 바뀌지 않으며 읽는 쪽은 두 판을 모두 받는다. 봉인·해시는 행마다 본문 그대로 걸린다.

판정이 외부 취소로 끝나면(호출한 쪽이 요청을 취소한 경우) 남은 판정 예산 안에서 `MINT-CANCELLED`(전송 전) 판정 사건을 같은 순서(데이터베이스, 버퍼, 표준 오류)로 남기고 취소를 그대로 다시 전파한다. 버퍼 기록은 예산이 소진되어도 한 번 시도한다. 판정 사건이 이미 어느 위치에든 기록된 뒤의 취소는 추가로 기록하지 않는다. 기록 도중에 취소되어 결과가 불명이면 취소 사건은 그 호출에서 이미 기록을 시작한 가장 큰 시도 번호보다 하나 큰 시도로 남는다(진행 중이던 감사 실패 차단 사건과 키가 겹치지 않는다). 도구 목록 판정의 취소는 기록하지 않는다.

- 표준 오류의 증거는 재적재 대상이 아닌 최후의 참조이다. 보존 기간은 컨테이너 로그 드라이버 설정에 달려 있다.
- 버퍼는 50MB를 넘으면 가장 오래된 파일을 지우고 유실 건수를 `buffer_overflow` 사건에 기록한다.
- 버퍼 디렉터리를 여러 프로세스가 함께 쓸 때의 상한과 고아 파일 복구는 파일 잠금에 기대므로 Linux에서만 보장한다. 재적재 중에 종료한 프로세스가 남긴 파일과 쓰는 프로세스가 없는 열린 파일은 잠금으로 판별해 다음 재적재가 이어받는다. 파일 잠금이 없는 Windows에서는 한 프로세스 안의 스레드 사이만 직렬화하며, 프로세스 사이의 상한도 이 자동 복구도 보장하지 않는다. 지원하는 배포는 Linux 컨테이너이다.

## 4. 집행하지 않는 경로

- **`prompts/*`, `resources/*`.** LiteLLM이 이 요청에 훅을 제공하지 않고 서버별·전역으로 끌 수도 없다. MINT는 이 요청을 판정하지도 기록하지도 않는다. 해당 정책은 수동 증거로 관리한다. 서버가 Prompt·Resource를 제공하는지 확인하고 열람 기록을 보관해야 한다.
- **`/mcp/proxy` 면.** 고정 도구 3개를 노출하는 이 면의 `tools/call`이 MINT 판정 훅을 지나는지는 아직 확인하지 않았다. 확인되기 전까지 이 면을 통한 호출은 판정된다고 보장하지 않는다.
- **목록에서 숨긴 도구의 직접 호출.** 목록에서 숨긴 도구는 LiteLLM의 도구 경로표에 등록되지 않는다. 같은 프로세스에서 다른 키가 그 도구를 먼저 목록화하지 않았다면, 직접 호출은 MINT 판정에 닿기 전에 LiteLLM이 「도구를 찾을 수 없다」로 거절할 수 있다. 호출은 업스트림으로 나가지 않지만 이때의 오류에는 MINT 사유 코드가 없다. 판정 사유는 도구가 목록에 한 번 노출된 뒤의 호출에서 기록된다.
- **설명과 스키마가 비어 있는 도구.** LiteLLM은 설명과 입력 스키마가 모두 없는 도구에는 목록 훅을 부르지 않으므로, 이런 도구는 판정과 사건 없이 목록에 보인다. 이 도구의 호출은 호출 판정을 지난다.
- **공급자 쪽 MCP 차단이 보지 못하는 요청.** 이 차단은 `pre_call` 단계를 지나는 요청 본문만 본다. 에이전트나 SDK가 모델 요청과 따로 외부 MCP 서버에 직접 연결하는 경우, `type`이 `mcp`가 아닌 공급자 고유 형식으로 MCP 연결을 지시하는 본문, 업로드한 입력 파일을 따로 처리하는 배치 요청은 판정하지 않는다. 값이 비어 있는 `mcp_servers`(빈 목록·null)는 공급자에게 연결을 지시하지 않으므로 통과시킨다. 패스스루 경로는 본문이 JSON 객체일 때만 위 항목을 찾는다. 연결 뒤 실시간 메시지는 위 「실시간 경로 거부」를 따른다. 배포 설정에서 `pre_call` 모드를 빼면 자가 점검이 집행을 확인하지 못해 기동이 멈추므로 이 차단을 설정만으로 끌 수 없다.
- **구독 중계(`subscriptions/listen`, `resources/subscribe`).** LiteLLM 1.108 이후는 업스트림 서버의 목록 변경·리소스 갱신 알림을 클라이언트에 이어 주는 요청을 추가했다. 이 요청은 `pre_mcp_call`·`post_mcp_call` 훅을 거치지 않으며 서버별·전역으로 끄는 설정도 없다(`mcp_disabled_capabilities`는 `prompts`·`resources`의 목록·읽기 요청만 끈다). 새 규격(`2026-07-28`)의 `subscriptions/listen`은 `mcp_advertised_versions`에 그 규격을 넣어야만 열리므로, MINT 자가 점검(8번 항목)은 이를 넣은 구성을 필수 설정 위반으로 보고 기동을 멈춘다. 기존 규격의 `resources/subscribe`는 MINT가 막지 못한다. 업스트림이 구독을 지원하고 살아 있는 세션이 있을 때만 동작하며, 이 경로로 가는 것은 알림이고 도구 호출 결과가 아니다. 해당 정책은 수동 증거로 관리하며, 이 요청을 판정하지도 기록하지도 않는다.
- **알림과 기타 메서드.** `notifications/*`는 업스트림으로 전달되지 않고, 그 밖의 메서드는 LiteLLM이 지원하지 않는다.
- **마스터 키의 도구 목록.** 마스터 키로 요청한 도구 목록은 모두 숨기고 호출은 차단한다. LiteLLM 관리 화면에서 MCP 도구를 시험할 때는 사용자 키를 쓴다.
- **LiteLLM 데이터베이스 직접 조작.** 직접 변경한 서버·권한은 실행 중인 워커에 반영되지 않을 수 있다. 제어 평면과 플러그인은 LiteLLM 데이터베이스를 읽거나 쓰지 않는다.

## 5. LiteLLM 설정에 달린 한계

- **지출 로그의 도구 인자.** LiteLLM은 도구 호출 인자를 지출 로그 메타데이터에 저장하고 `/spend/logs`로 관리자와 일반 사용자가 읽을 수 있다. `store_prompts_in_spend_logs: false`나 메시지 로깅 중지로는 막을 수 없다. 막으려면 `disable_spend_logs: true`로 지출 추적 전체를 꺼야 하며, `init --no-spend-logs`를 줄 때만 설정 조각에 넣는다. `store_prompts_in_spend_logs: true`는 도구 결과 본문까지 저장하므로 통제 대상 배치에서 금지한다. 외부 콜백(OTEL, Langfuse 등)이 켜져 있으면 인자가 그 서비스로 전달된다. MINT는 다른 콜백의 입력을 바꾸지 않는다. `check`와 `status`는 `spend_log_arguments_stored`를 표시한다.
- **판정이 보지 못하는 인자 변경.** 병렬 단계의 다른 가드레일이 공유 `data`를 제자리에서 바꾸는 경우(LiteLLM의 차단 전용 계약 위반)와, 다른 병렬 가드레일이 민감 데이터 라우팅 예외(`SensitiveDataRouteException`)를 던져 LiteLLM이 `data`를 고쳐 이어 가는 경우(도구 인자에 미치는 영향은 통합 시험에서 확인한다)와, 사전 훅 호출 밖에서 인자를 바꾸는 경로는 판정이 알 수 없다. 앞선 순차 가드레일이 수정본을 만들지 않고 `mcp_arguments`와 첫 메시지를 함께 바꾸는 구성은 원래 인자 확인을 통과하므로 판정한 인자와 전송되는 인자가 갈릴 수 있다. 이 구성은 지원 범위 밖이다. 정책 파이프라인이 MINT 가드레일을 관리하도록 설정하거나 같은 이름의 가드레일을 여러 개 배포하는 관리자 설정에서는 MINT 판정이 건너뛰어질 수 있다. 판정 뒤에 병렬 단계의 다른 가드레일이 호출을 막으면 이미 소비된 호출별 승인은 되돌리지 않고, 실패 이벤트로 전송 전 차단임을 확정할 수 없으므로 `call_outcome_unknown` 사건에 그 승인 식별자를 남긴다.
- **수정본 없이 인자만 바꾸는 순차 가드레일.** LiteLLM 전송부는 참인 수정본이 없으면 훅에 들어오기 전의 원래 인자를 보낸다. 가드레일이 수정본 없이 사전 훅 데이터의 `mcp_arguments`만 다른 객체로 바꾸면(예: 도구 인자 마스킹을 이 방식으로 하는 내장 가드레일) MINT는 판정한 인자와 전송될 인자가 같다고 확인할 수 없어 그 호출을 `MINT-SCHEMA-ERROR`로 차단한다. 그런 가드레일은 수정본을 돌려주도록 구성해야 MINT와 함께 쓸 수 있다. 반대로 `mcp_arguments`와 첫 메시지를 함께 같은 값으로 바꾸면서 수정본을 만들지 않는 순차 가드레일은 이 확인을 통과하므로 MINT가 판정한 인자와 LiteLLM이 보내는 원래 인자가 갈릴 수 있다. 이런 구성은 지원 범위 밖이며 MINT가 막지 못한다. `mcp_arguments`가 원래 인자와 같은지는 변환기가 첫 메시지 끝에 남기는 원래 인자의 문자열로 확인하며, 기동 점검(호환 심볼 항목)이 지원 판본의 변환기가 알려진 원래 입력과 같은 문자열을 이 자리에 남기는지 직접 대조해 확인한다.
- **데이터베이스 복구 직후와 기동 직후.** 데이터베이스가 돌아온 뒤 연결 풀이 연결을 다시 만드는 동안(수 초)의 호출과, 기동 직후 동시 호출이 몰려 연결이 모자란 호출은 `MINT-DEPENDENCY-DB`(재시도 안전)로 막힐 수 있다. 호출을 막는 쪽의 오류이므로 집행은 유지된다. 서버가 끊은 연결은 한동안 쓰지 않았다면 쓰기 전에 확인해 버리지만, 연결 풀은 처음 열 때 `MINT_DB_POOL_SIZE`개를 모두 만든 뒤 쓰지만, 재연결이 끝나기 전의 호출은 여전히 막힐 수 있다.
- **가드레일 제외 키.** 키·팀의 `metadata`에 `opted_out_global_guardrails`나 `disable_global_guardrails`가 있으면 LiteLLM이 그 키·팀의 가드레일을 건너뛴다. MINT 판정은 병렬 MINT 가드레일이 맡고 이 가드레일은 제외 설정과 무관하게 항상 실행되므로, MINT 판정과 도구 목록 숨김은 그대로 적용되고 꺼지는 것은 다른 가드레일뿐이다. 일반 사용자가 이런 키를 만들지 못하도록 `personal_key_generation.allowed_user_roles: ["proxy_admin"]`를 권장하며, `check`가 다른 가드레일을 끈 키·팀 수를 관측 항목 `guardrail_optout_subjects`로 표시한다. 이 항목은 실패 조건이 아니다.
- **권한 캐시.** LiteLLM의 키·팀·`object_permission` 캐시는 프로세스 메모리에 60초(`user_api_key_cache_ttl`) 머무르고, Redis가 없으면 무효화가 복제본 사이에 전파되지 않는다. MINT의 상태는 MINT 데이터베이스를 직접 읽으므로 이 지연과 무관하다.
- **속도 제한.** 서버 `rpm`과 키·팀 `mcp_rpm_limit`은 LiteLLM 기능을 그대로 쓰며 Redis가 없으면 프로세스별로 계수된다. 사용자·조직 단위 한도는 제공하지 않는다. `LEGACY_MULTI_INSTANCE_RATE_LIMITING=true`이면 `mcp_rpm_limit`이 집행되지 않는다.
- **통제 서버의 식별.** 설정 서버는 `server_id`를 명시해야 한다. 명시하지 않으면 URL 등이 바뀔 때 식별자가 바뀌어 기존 권한이 어긋난다. 같은 이름·별칭의 서버가 둘 이상이면 호출을 차단한다. 서버의 계약 값은 레지스트리 URL 문자열의 SHA-256(끝 슬래시와 대소문자를 포함해 정규화하지 않음), 전송 방식, 인증 방식이며 인증이 없는 서버의 인증 방식은 `none`이다. 셋 중 하나라도 달라지면 그 서버의 호출을 차단한다. 기동할 때 계약 값이 다른 서버가 있으면 프록시는 기동을 이어 가며 달라진 항목을 사건으로 남긴다.
- **도구 목록의 시점 일관성.** 목록 처리는 도구마다 상태 스냅숏을 읽는다. 목록 전체가 한 시점의 상태를 반영함은 보장하지 않는다. 판정 시간 예산도 도구마다 쓰며 목록 전체의 제한 시간은 LiteLLM의 목록 제한(`LITELLM_MCP_TOOL_LISTING_TIMEOUT`)에 따른다. 한 도구의 판정이 시간 초과이거나 의존 서비스를 쓸 수 없으면 집행 모드에서 그 도구를 숨긴다.
- **재시작 직후 목록 단계 차단의 표시.** 방금 시작한 LiteLLM은 호출 전에 도구 목록을 만들고, MINT는 이 단계에서 도구마다 차단 판정을 낸다(예: 내보내기 검증 실패 `ENFORCEMENT_UNVERIFIED`, 미등록 서버 `SERVER_UNREGISTERED`). LiteLLM이 이 예외를 「도구 없음」으로 바꾸므로 호출자에게는 MINT 차단 코드가 아니라 HTTP 500 「Tool not found」로 보인다. 차단 자체는 성립하고 업스트림 호출은 없으며, 차단 판정은 MINT 사건과 로그에 코드와 함께 남는다. 목록이 이미 만들어진 복제본은 호출 단계에서 코드가 있는 403을 낸다. 호출자 응답 본문으로 차단 사유를 가려내는 점검은 재시작 직후에는 쓸 수 없고, 사건의 판정 사유를 본다.
- **기동 전 설정 검사.** MINT가 제공하는 파생 이미지의 진입점이 LiteLLM을 시작하기 전에 설정 파일을 검사한다. 운영자가 진입점을 덮어쓰면 기동 전 검사가 사라진다. 순정 LiteLLM 이미지를 직접 쓰는 구성도 이 검사를 받지 않으며, 운영 중에는 `check`가 관리 API로 확인한다.
- **정책 번들 내용의 검증 시점.** 활성화는 OPA가 적재한 규칙 원문과 정책 데이터에서 번들 해시를 다시 계산해 등록된 값과 대조하고, 호출 때는 판본 식별자와 해시 메타만 대조한다. 활성화와 다음 `check` 사이에 OPA의 내용이 바뀌면 그 `check`까지 탐지하지 못한다. 재계산은 규칙이 만든 문서와 `data.mint.data`·`data.mint.meta`가 아닌 데이터가 OPA에 있으면(번들 안 다른 경로의 데이터 파일 포함) 불일치로 거부한다. `data.system` 아래는 번들 목록(`etag`·`manifest`)과 판본 정보의 정해진 키와 형식만 허용한다. 지원하는 적재 경로는 파일 번들과 감시(`--watch`)이며, 설정 기반 번들 플러그인 경로는 판본 정보를 다시 쓰지 않으므로 지원하지 않는다.
- **활성화 실패 시 이전 번들 복원.** 게시 직전에 현재 번들 파일이 활성 판본의 온전한 번들(판본 ID와 내용 해시가 일치하고 내용에서 다시 계산한 해시와도 같음)이면 같은 디렉터리에 `.previous`로 보관한다. 게시를 시작한 뒤 활성화가 실패하면(적재 내용 불일치, 시간 초과, 취소, DB 확정 실패) 잠금 안에서 DB의 활성 판본을 다시 읽어 그 판본과 일치하는 보관본으로만 되돌리고, OPA가 그 메타와 내용을 다시 서빙하는지 확인한다. 복원 시간은 전체 제한에서 먼저 떼어 두며, 남은 몫이 1초보다 작으면 복원에 최대 1초를 더 쓴다. 제한은 하나이며 잠금 대기·DB 전환·커밋도 포함하므로 DB가 응답하지 않아도 제한에서 끝난다. 새 연결을 만드는 함수를 주면 문장 도중 취소되었거나 끊긴 연결은 정리하고 새 연결로 활성 판본을 다시 읽어 복원 여부를 판정한다. 게시 함수는 취소되면 쓰기를 남기지 않아야 한다. 결과(`restored`, 활성 판본 없음, 일치하는 보관본 없음, 활성화가 이미 확정됨, 연결 소실로 확정 여부 불명, 복원 실패·중단)는 던져지는 오류에 담긴다. 한계: 첫 활성화는 되돌릴 판본이 없어 새 번들이 서빙된 채 호출이 판본 불일치로 차단되며 정상 번들로 다시 시도해야 한다. 연결이 끊겨 커밋 결과를 알 수 없으면 복원하지 않으므로 운영자가 상태를 확인해야 한다. 게시 전 단계(보관 포함)의 실패는 파일을 건드리지 않는다.

- **기동 전 검사가 보지 못하는 설정 출처.** 기동 전 검사는 LiteLLM의 설정 로더가 읽은 파일 설정과 시작 시점의 환경을 본다. LiteLLM이 기동 중에 비밀 관리자에서 받는 값, 데이터베이스에 저장된 설정으로 보정되는 값은 볼 수 없다. 설정 경로를 환경 변수로 바꿀 수 있는 입력(`CONFIG_FILE_PATH`, 설정 버킷 변수, `.env`, `USE_AWS_KMS`와 설정 경로 별칭의 조합)은 시작 전에 거부하지만, 배포 설정을 쓸 수 있는 사람이 의도적으로 우회하는 것은 막지 못한다. 운영 중에는 `check`가 관리 API로 확인한다. 로더로 해석할 수 없는 출처는 시작을 거부한다.
- **검사와 기동 사이.** 기동 전 검사와 LiteLLM의 적재는 설정 파일을 각각 읽는다. 그 사이에 파일이나 심볼릭 링크가 바뀌면 검사한 내용과 적재한 내용이 다를 수 있다. 설정 파일을 쓸 수 있는 사람은 읽기 전용으로 마운트해 이 구간을 닫아야 한다.
- **비밀 파일의 경로 검사.** 이미 있는 비밀 파일은 열어 둔 디렉터리·파일 기술자 기준으로 검사하지만, 새 파일을 만들 때의 디렉터리 확인과 임시 파일 생성·게시는 경로 기준이다. 마지막 디렉터리보다 위의 경로 구성요소가 심볼릭 링크인 것은 막지 않는다. 다른 사용자가 쓸 수 없는 위치에 두어야 한다.

## 6. OAuth 보호의 범위

OAuth 흐름은 LiteLLM의 기능을 재사용하며, 아래 조건이 설정되어 있을 때만 해당 보호가 성립한다. MINT는 설정 점검과 허용 목록 대조만 보강하고 흐름을 다시 구현하지 않는다.

| 통제 | 필요한 설정 |
| --- | --- |
| 인가 서버 고정 | `mcp_servers.<이름>.issuer` 명시 |
| 수신처 제한 | `PROXY_BASE_URL`, `MCP_TRUSTED_REDIRECT_ORIGINS`, 역프록시 뒤라면 `use_x_forwarded_for`와 `mcp_trusted_proxy_ranges` |
| 상태·nonce·PKCE | `oauth_identity_binding.mode: enforce` |
| 조회 주소 제한 | `user_url_validation: true`(기본값) |

다음 하위 통제는 지원하지 않는다. 필요하면 앞단 역프록시와 egress 통제로 보완한다.

- 일부 릴레이 방식의 `state` 만료와 서버 측 1회 소비가 없어 재사용된 결과를 거부하지 못한다(통합 시험으로 확인: 쿠키가 남아 있으면 같은 콜백이 되풀이해서 통과한다).
- 인가 서버가 메타데이터로 응답에 `iss`를 싣는다고 알리지 않으면 `iss`가 없는 응답을 받아들인다. 발급자를 고정해도 `iss`를 싣지 않는 바꿔치기 응답은 막지 못하고, `iss`가 있으면서 다른 값인 응답만 거부한다.
- `enforce` 모드 밖의 릴레이 방식은 PKCE를 업스트림에 위임한다.
- 동적 클라이언트 등록(DCR) 브리지 릴레이는 `redirect_uri`를 검증하지 않는다.
- 동적 클라이언트 등록(`/register`)은 인증이 없고 등록 수와 속도 제한이 없다.
- 같은 권한 URL, 초기 프로브, 토큰·등록 POST, 보호 리소스 메타데이터 릴레이, JWKS 조회는 주소 검증을 거치지 않는다.
- 인가 서버 허용 목록은 LiteLLM이 제공하지 않으므로 MINT 허용 목록(`allowlist add`)으로 승인 근거를 대조한다.

## 7. 신원의 한계

- 최종 사용자 식별자(`claimed_end_user_id`)는 호출자가 헤더나 본문으로 바꿀 수 있는 주장 값이다. 범위를 좁히는 데만 쓰고, 승인·동의의 주체로 쓰지 않는다.
- 사용자·팀·키 식별자는 LiteLLM이 검증한 값이며 호출자가 바꿀 수 없다.
- 서비스 계정 표식(사용자 없음, 팀 있음, `service_account_id` 메타데이터)은 일반 키 생성으로도 만들 수 있어 단독으로는 서비스 계정의 증명이 아니다.
- LiteLLM 오픈소스에는 조직 권한이 없으므로 MINT 조직은 팀·사용자 바인딩(`org bind`)과 기본 조직으로 유도한다. 바인딩이 없고 기본 조직도 없으면 호출은 차단된다.
- 사용자도 팀도 없는 키와 키 없이 들어온 요청은 신원을 확정할 수 없어 익명으로 보고 항상 차단한다. `check`와 `status`가 이런 키의 수를 `unbound_keys`로 표시한다.
- 키 없는 주체. LiteLLM의 JWT 인증(`proxy/auth/handle_jwt.py`의 `user_api_key_auth_from_result`)은 `api_key=None`으로 `UserAPIKeyAuth`를 만들어 `token`이 없고 `user_id`·`team_id`·`org_id`·`end_user_id`·`agent_id`·`jwt_claims`만 채운다. 관리형 에이전트(`autonomous`·`delegated`)도 같은 경로이며 `managed_agent_context`가 붙는다. 게이트웨이 입장 사용자는 서버만 설정하는 `mcp_admitted_user_subject`가 참이다. MINT는 이 셋 중 하나가 있고 `user_id`가 있으면 그 사용자로 판정한다(`key_id` 없음). 이때 사용자 범위 허용·동의·호출 승인은 `user_id`로 맞고, 키 범위 허용은 맞지 않는다. 확인(본인 확인)은 요청과 확인에 키 토큰이 필요하므로 키 없는 사용자는 요청을 만들지 못해 `MINT-CONFIRMATION-REQUIRED`로 남는다. 위 표지가 없는 키 없는 객체, `user_id`가 없는 JWT(팀만 있어도), 사용자 ID가 비어 있는 경우는 `MINT-ANONYMOUS`로 막는다. 에이전트가 자율(`autonomous`)로 호출할 때의 `user_id`는 LiteLLM이 정한 값을 그대로 쓰며, MINT가 사람과 에이전트를 구분하지는 못한다. 마스터 키는 LiteLLM이 별칭으로 바꿔 넣으므로 키 있는 경로로 남는다.
- 마스터 키로 들어온 도구 호출은 차단한다.
- 「사람 사용자」는 LiteLLM 사용자 역할 분류에 의존한다. MINT는 그 사용자가 실제 사람인지 독립적으로 검증하지 못한다.

## 8. 동의의 증명

동의는 운영자가 서명된 동의서나 사내 시스템 기록의 참조와 해시를 붙여 등록한다(`operator_attested`). 증거 참조와 해시가 없으면 등록이 거부된다. 본인이 직접 동의했는지는 운영자의 증명에 의존하며 MINT가 독립적으로 확인하지 못한다.

## 9. 지원하지 않는 기능

다음 기능이 필요한 정책은 호출 전에 `MINT-UNSUPPORTED`로 차단된다.

- 인자 변환 의무(키 제거, 크기 제한, 값 치환 등)
- 결과 본문을 다른 값으로 고치는 출력 변환(결과 검사와 비밀·개인정보 가리기는 아래 안내대로 한다)
- OpenAPI 명세로 만든 MCP 서버처럼 URL이 없는 서버. `server register`가 등록을 거부하고, 호출은 `MINT-UNSUPPORTED`로 차단한다. 로컬 실행(stdio) 서버는 `server register-local`로 실행 계약을 등록해 통제한다(아래 9-1).

계약 관리 서버는 승인된 도구 계약의 입력 스키마 드리프트, 승인 없는 도구, 배포 드리프트, 관측 기한 초과를 판정한다. 관측 주기는 `MINT_OBSERVE_SECONDS`이며 마지막 관측이 없거나 두 주기를 넘기면 차단한다. 설명·annotations·기존 출력 스키마의 변경은 경보와 재승인 요청만 만든다. 계약 관리가 아닌 서버는 기존 판정 경로를 유지한다.

관측은 수용검증 클라이언트의 업스트림 시험 목록 연결을 필요로 한다. 해당 연결이 없거나 자격·응답 검사에 실패하면 성공 시각을 갱신하지 않는다. LiteLLM이 호출자에게 제공한 목록을 원본 관측의 대용으로 쓰지 않는다. 재승인은 후보에 결속된 최신 검사 증거와 실제 재pin 해시가 일치해야 끝나며, 외부 pin 실패 뒤에는 기존 승인본과 임시 차단을 유지한다. 제어 키의 도구 목록 면제는 부정 상태·익명·마스터 키에는 적용되지 않고, 제어 키의 도구 호출도 항상 차단한다.

도구 결과 검사는 호출이 허용된 뒤 결과를 호출자에게 주기 전에 한다. 승인 조건 `max_result_bytes`·`max_result_items`를 넘거나, 결과 본문이나 구조화된 결과(`structuredContent`)의 문자열에 지시문 표지(이전 지시 무시, 역할 표지, 사용자에게 숨기라는 문구)가 있으면 결과 대신 `MINT-OUTPUT-BLOCKED`를 돌려주고 응답 사건의 `output_findings`에 정책 식별자를 남긴다. 관측 모드에서는 막지 않고 사건에만 남긴다. 본문과 구조화된 결과의 문자열은 겹치는 조각으로 나눠 끝까지 훑는다(합쳐서 `MINT_SCAN_MAX_CHARS`, 기본 3,355만 글자까지). 상한을 넘으면 집행 모드(계약 관리가 아닌 서버는 `MINT_SCAN_UNMANAGED=enforce`일 때)는 결과를 막고(`MINT-RESULT-SCAN-LIMIT`), 관측에서는 응답 사건의 `scan_truncated`에 남긴다. 검사 코드가 오류를 내면 집행 모드는 결과를 막는다(`MINT-RESULT-SCAN-ERROR`). 한계: 업스트림은 이미 호출을 수행한 뒤이고, 지시문 표지는 정규식으로 보는 휴리스틱이라 변형된 문구나 표지에 없는 문장은 놓치며 모델이 결과의 지시를 따르지 않는다는 보장은 아니다. 상한을 넘는 뒷부분은 관측에서는 보지 않는다. 결과가 클수록 검사 시간이 늘어 응답이 늦는다(1MiB에 약 0.2초, 8MiB에 약 1.5초). `MINT_SCAN_MAX_CHARS`를 낮추면 지연이 줄지만 상한을 넘는 결과는 집행 모드에서 막힌다. 결과 상한은 승인 조건을 준 호출에만 적용한다.

계약 관리가 아닌 서버에도 같은 지시문 표지 검사(POL-E-04)와 호출 인자의 비밀·식별번호 검사(POL-E-05)를 적용한다. 기본(`MINT_SCAN_UNMANAGED=observe`)에서는 호출과 결과를 막지 않고 응답(또는 결과 불명) 사건의 `unmanaged_findings`와 `server_id`에 남기며, 작업 실행기가 최근 15분의 그런 사건을 모아 서버마다 경보 `content_finding_unmanaged`를 한 번 연다(미해결인 동안 다시 열지 않고, 닫는 일은 운영자가 한다). `enforce`로 두면 계약 관리 서버와 같이 막는다. 판정 경로에 DB 왕복은 늘지 않으며 검사 비용은 결과 1MiB당 수십 밀리초 규모이다. 한계: 관측 기본값에서는 그 호출의 결과가 호출자에게 그대로 가고, 인자 검사는 호출 판정이 허용으로 끝난 호출만 사건에 남는다. 결과 크기·항목 수 상한(POL-E-16)과 비밀·개인정보 가리기는 이 설정과 무관하다.

결과의 비밀·개인정보 검사는 허용된 호출의 결과 본문에서 개인 키, 클라우드 접근 키, GitHub 토큰, Bearer 토큰, JWT, 주민등록번호, 전화번호, 이메일, 카드 번호(Luhn 검증)를 찾는다. 승인 조건 `response_scan`을 주지 않으면 `mask`로 동작해 찾은 값만 `[MASKED:종류]`로 바꿔 호출자에게 주며, `block`이면 결과를 `MINT-OUTPUT-BLOCKED`로 막고 `observe`이면 기록만 한다. 관측 모드에서는 값에 상관없이 기록만 한다. 응답 사건에는 탐지 종류별 건수만 남고 일치한 값은 남지 않는다. 외부 서비스를 부르지 않는 내장 정규식·검증식이며, 문서의 예시 키(`…EXAMPLE`)와 예약 도메인(`example.com` 등)의 이메일은 건너뛴다. 한계: 공백·분할·인코딩으로 변형한 값은 놓치고, 2020년 10월 이후 발급된 주민등록번호는 하이픈 형식만 날짜 검증으로 잡으며, 이름·주소 같은 자유 서술 개인정보는 찾지 못한다. 구조화된 결과(`structuredContent`)의 문자열 값과 키도 같은 검사를 받고, 걸리면 응답 사건의 `finding_paths`에 JSON 경로만 남긴다(값과 비밀로 보이는 키는 남기지 않는다). 구조화된 결과의 개인정보(이메일·전화번호·주민등록번호·카드 번호)는 경로만 남기고 결과를 막지 않는다(커밋 작성자 이메일 같은 정상 값이 많다). 알려진 형식의 비밀(개인 키, 클라우드 접근 키, 토큰, JWT, Bearer)은 구조화된 결과에서는 가릴 수 없으므로 `mask`에서도 걸리면 결과를 막는다. 비밀처럼 보이는 긴 문자열(32자 이상, 숫자를 섞은 높은 무작위성)은 종류 `high_entropy_token`으로 `sensitive_findings`에 건수만 남기고 결과를 막거나 가리지 않으며, 계약 관리가 아닌 서버는 경보 `content_finding_unmanaged`에도 오른다. UUID·16진수 해시·이미지 base64·해시 필드(`sha`·`etag` 등)의 값은 빼지만, 무작위로 보이는 일반 식별자(예: GitHub `node_id`)는 오탐할 수 있고 `-`·`_`로 짧게 끊긴 비밀은 놓친다. 검사 상한(`MINT_SCAN_MAX_CHARS`)을 넘는 결과는 끝까지 볼 수 없어 `mask`와 `block`에서 결과를 막는다(`scan_limit`). 업스트림은 이미 호출을 수행한 뒤다. LiteLLM의 Presidio 같은 가드레일은 영어 위주이고 라이브러리가 없으면 가리지 않고 통과시키므로, 필요하면 운영자가 따로 켜서 함께 쓴다(MINT는 켜 두었는지 확인하지 않는다).

이용 관계를 종료하면 그 관계의 활성 승인을 바로 철회하고, 작업 실행기가 철회한 승인이 가리키던 키·팀의 LiteLLM 권한을 읽어 MINT가 넣은 서버 권한이 모두 거두어졌을 때 결과(대상, MINT가 넣지 않아 남은 권한)를 `relation_terminating` 사건(`phase: revocation_confirmed`)에 한 번 남긴다. 관계를 `terminated`로 닫는 일은 증빙을 확인하는 `relation finish`가 하며, 회수 확인을 기다리지 않는다. 거두지 못한 항목이 있으면 경보 `termination_unconfirmed`를 연다. 한계: 사용자(`user`)·조직(`org`) 범위 승인은 LiteLLM 권한을 동기화하지 않으므로 읽어 확인할 대상이 없고, 승인 없이 LiteLLM에서 직접 준 권한은 MINT가 거두지 않는다(결과의 `retained`에 적는다). 종료 중에 대기 중이던 승인은 철회하지 않는다.

같은 서버 식별자를 계약 관리하는 인스턴스가 둘 이상이면 작업 실행기가 관측 주기마다 인스턴스별 승인 계약(배포, 도구 정의)의 해시를 비교해 다르면 경보 `instance_mismatch`와 배포 변경 사건을 남긴다. 비교 대상에는 승인 계약 외에 인스턴스가 DB에 기록한 보안 설정(가드레일 모드, 활성 정책 묶음 해시)도 든다. 어긋나면 경보는 바로 열고, 차이를 처음 본 시각부터 `MINT_INSTANCE_MISMATCH_GRACE_SECONDS`(기본 900초, 0이면 바로)가 지나도 남아 있으면 기준 인스턴스를 따로 두지 않고 어긋난 인스턴스 모두가 그 서버 호출을 사유 `CONTRACT_DRIFT_instance_mismatch`로 막는다(관측 모드로 풀 수 없다). 정책 묶음 활성화나 계약 배포를 인스턴스마다 차례로 하는 동안은 유예 안에 끝내야 막히지 않는다. 처음 본 시각은 관측 때마다 다시 세지 않고 차이가 사라지면 지운다. 판정은 계약 관측 작업이 도는 주기(`MINT_OBSERVE_SECONDS`)마다 이루어지므로 실제로 막히는 시점은 유예 뒤 첫 관측이다. 차이를 없애거나 admin이 서버에 `instance_exception` 증빙(30일 이하)을 붙이면 다음 관측 주기에 풀린다. 같은 서버를 쓰는 인스턴스가 하나뿐이면 영향이 없다. 한계: DB를 공유하지 않는 인스턴스와 서로 다른 서버 식별자로 등록한 같은 서비스는 비교하지 못하고, 호출 한도 같은 설정은 비교하지 않는다. 예외 증빙은 차이의 내용이 아니라 서버에 붙으므로 기한 안에서는 이후 새로 생긴 차이도 풀어 둔다.

## 9-1. 단말 설치 묶음의 범위

- 첫 구간은 Linux와 Claude Code이다. 관리형 설치(관리자 권한)에서만 훅·MCP 목록·에이전트가 관리자 소유 경로에 놓이고, 사용자 수준 설치는 사용자가 바꿀 수 있어 MINT에 「관리되지 않음」으로 보고된다. 보고는 단말의 주장이며 MINT가 관측한 사실이 아니다.
- 서버 시작 통제는 설치 묶음이 만든 실행기가 한다. 실행 파일은 검증한 기술자로 실행하지만 셸 스크립트와 서버가 읽는 스크립트는 경로로 실행·열람되어 검증과 실행 사이의 교체를 완전히 막지 못한다. 시작 뒤 서버가 부르는 자식 도구의 변경도 검사하지 않는다.
- 사용자 수준 설치에서는 묶음의 서버 목록에 없는 MCP 서버의 호출도 훅이 막는다(승인된 계약이 없기 때문이다).
- 묶음의 사용자 키는 `MINT_ENDPOINT_KEY_DAYS`(기본 90일) 뒤 만료된다. 만료된 키의 보고는 거부되고, 만료 14일 안에 들어온 정상 보고가 기간을 늘린다. 새 묶음을 내려받거나 「연결 해제」를 하면 키가 지워진다.
- 로컬 서버 정책(POL-R-18·POL-R-20)은 호출 때 승인된 실행 계약과 보고된 계약을 대조해 막고, 관리형 설치에서는 서버 실행기가 승인된 계약과 맞을 때만 서버를 시작하는 조건부 충족이다. 관리형이 아닌 사용자 수준 설치와 하네스 밖에서 직접 시작되는 서버는 막지 못하며, 호출 때의 대조는 단말이 보고한 실행 정의에 대한 것이지 실행 중 프로세스의 증명이 아니다.
- 서버 폐기(POL-D-03): `server terminate` 뒤 LiteLLM에 저장된 사용자별 OAuth2 토큰·API 키를 지우고 목록을 다시 읽어 비었을 때만 폐기됨으로 닫는다. 서버 자체 비밀·사용자별 환경 변수·동적 등록 클라이언트는 LiteLLM이 목록·삭제 경로를 주지 않아 확인하지 못하고, 업스트림 쪽 토큰 해지는 하지 않는다.
- 폐기된 서버 항목이 설치 보고에 남아 있으면(POL-D-02) 경보 `endpoint_stale_server`가, 사용자 수준 설치(POL-E-06이 적용되지 않는 설치)면 경보 `endpoint_unmanaged`가 열린다. 게이트웨이 밖 MCP를 막는 것은 관리형 설치뿐이다. 둘 다 단말의 보고에 기대므로 협조적인 단말에서만 정확하다. 설치·제거 보고에는 단말이 보는 묶음 실행기 프로세스와 자동 시작 항목(Linux는 사용자 systemd 단위·자동 시작 파일·`@reboot` 크론, Windows는 Run 키·예약 작업·시작 프로그램 폴더)도 담기며, 승인 상태가 아니거나 레지스트리에 없는 서버를 가리키면 경보 `endpoint_stale_process`·`endpoint_stale_autostart`가 열리고(POL-D-04) 사라지면 닫힌다. 설치한 묶음은 systemd 타이머(Linux: 관리형은 시스템 타이머, 사용자 수준은 사용자 타이머)·예약 작업(Windows: 관리형은 SYSTEM 계정)으로 6시간마다(최대 30분의 무작위 지연), 그리고 서버 실행기가 시작될 때(1시간에 한 번까지) 같은 보고를 다시 보내 목록을 갱신하며, 보고가 24시간 넘게 끊기면 경보 `endpoint_silent`가 열린다(켜져 있지 않은 단말도 같다). 묶음의 키는 90일 뒤 만료되고 만료 14일 안의 보고가 늘려 주며(보고가 끊긴 단말의 키만 만료된다), 만료 7일 안이면 `endpoint_key_expiring`이 열린다. 만료는 보고 경로에서 집행하고 결정 경로의 인증은 LiteLLM 키 그대로이므로, 훔친 키로 계속 보고하는 단말은 만료되지 않으며 연결 해제만이 키를 끊는다. 이 목록은 보고 시점의 단말 주장이며 묶음 실행기 밖에서 뜬 프로세스는 보지 못한다. 관리형 설치는 경보에 더해 스스로 정리한다(POL-D-02는 조건부, POL-D-04는 부분): 보고 응답이 폐기·반려·미승인 서버 이름을 돌려주면 관리자 권한으로 도는 보고기가 묶음이 쓴 관리형 설정 항목(Claude Code 관리형 MCP 목록, Codex 요구·서버 정의 파일과 표식 구간)과 묶음 실행기가 기록한 프로세스(PID와 시작 시각이 모두 맞을 때만)와 묶음이 등록한 자동 시작 항목만 지우고, 지운 항목을 곧바로 다시 보고해 항목마다 사건 `endpoint_remediated`를 남기며 경보는 다음 점검에서 닫힌다. 서버 실행기는 마지막 응답의 목록에 든 서버를 시작하지 않는다(목록이 오래되어도 유지하고, 목록이 없거나 읽을 수 없으면 막지 못한다). 사용자가 만든 항목과 묶음이 띄우지 않은 프로세스, 사용자 수준 설치는 건드리지 않고 경보만 남는다. 정리는 보고기가 돌 때만 일어나므로 타이머를 끄거나 단말이 꺼져 있으면 다음 보고까지 남고, 실행기가 읽는 목록은 사용자 캐시라 사용자가 지울 수 있다. 관리자 권한 보고기의 권한 모델은 다음과 같다. (1) 실행 신뢰: 보고기가 돌 때마다, 설치할 때도, 인터프리터·`mint_kit.py`·`kit.json`·설치 폴더와 그 상위 폴더 전부(링크를 따라간 실제 경로 포함)가 관리자 소유이고 그룹·모두가 쓸 수 없는지 확인하고 하나라도 어긋나면 보고하지 않고 끝난다. Windows는 소유자가 SYSTEM·Administrators이고 Users·Authenticated Users·Everyone에 쓰기 권한이 없는지 ACL로 본다. 관리형 설치는 사용자 가상 환경이 아닌 시스템 인터프리터(`/usr/bin/python3`)를 쓴다. (2) 사용자 홈 접근: Linux 보고기는 키·기록 파일 읽기, 마지막 보고 기록, 폐기 서버 목록 캐시, 인벤토리 읽기, 실행기 기록으로 프로세스 끄기, 자동 시작 파일 지우기를 모두 사용자의 uid·gid로 내려간 자식 프로세스에서 하므로(보조 그룹 없음) 사용자가 경로 중간을 심볼릭 링크로 바꿔도 커널이 사용자의 권한만 허용한다. 관리자 권한으로 chown하지 않으며, 계정은 `--user` 이름으로 계정부에서 찾는다. Windows SYSTEM 보고기는 사용자 프로필을 읽지도 쓰지도 않는다(경로를 점검한 뒤 쓰는 방식은 점검과 사용 사이의 경합을 막지 못하므로 쓰지 않는다). 설치할 때 관리자 권한으로 키 사본(`reporter.key`)을 설치 폴더에 두고(SYSTEM·Administrators만 읽음), 설치 폴더의 접근 권한을 SYSTEM·Administrators 쓰기, Users 읽기만으로 명시하며, SYSTEM 보고기는 마지막 보고 기록과 폐기 서버 목록(`retired.json`)을 같은 폴더에 쓰고 사용자 권한으로 도는 서버 실행기가 그 목록을 읽는다. 그래서 SYSTEM 보고기는 프로필의 시작 프로그램 폴더를 인벤토리에 넣지 않고, 사용자 설정 파일(Codex `config.toml`)의 항목·프로필 안의 자동 시작 파일·실행기가 프로필에 남긴 프로세스 기록은 건드리지 않는다(관리자 소유 요구 파일의 항목 제거와 실행기의 시작 거부가 그 몫을 막는다). (3) 관리형 설정 파일(`/etc/claude-code`, `/etc/codex`, ProgramData): 링크를 따라가지 않고(`O_NOFOLLOW`) 열고, 관리자로 돌 때는 root 소유이고 그룹·모두가 쓸 수 없는 파일만 고친다. 서버가 접근할 경로와 권한은 실행 계약의 `file_access`(경로와 읽기 또는 읽기·쓰기)에 선언해 계약 해시에 묶이며(POL-I-08) 늘어나면 재승인 전까지 호출이 막힌다. 선언은 관리형 설치에서 격리로 집행된다(POL-O-13·POL-I-08, 조건부). Linux는 서버 실행기가 승인된 계약에서 bubblewrap 명령을 만들어 서버를 그 안에서 시작한다(Windows는 아래 AppContainer 항목). 격리 안에는 시스템 읽기 전용 폴더(`/usr`·`/bin`·`/lib*`와 `/etc`의 몇 파일), 실행 파일과 그 묶음 폴더·스크립트 폴더·작업 디렉터리(읽기 전용), 선언한 경로(선언한 권한대로), 비어 있는 홈과 `/tmp`만 있고, 선언하지 않은 경로는 보이지 않는다. 네트워크는 계약이 `network: none`을 선언한 서버만 막히고(`server register-local --network none`, 계약 해시에 포함), 선언이 없거나 `any`인 서버는 제한이 없다(「네트워크 미제한」, 이전 승인 계약이 이에 해당). 계약이 `network: hosts`와 허용 호스트 목록(`--allow-host 호스트[:포트]`, 정확한 이름 또는 `*.도메인`, 계약 해시에 포함되며 목록이 늘어나면 네트워크 축 확대)을 선언하면 서버는 네트워크 없는 격리 안에서 시작되고, 서버 실행기가 연 중계(HTTP CONNECT와 `http://` 요청, 표준 라이브러리만)로만 나갈 수 있다. 중계는 선언한 호스트·포트만 잇고, 이름 해석을 스스로 하며(선언하지 않은 이름은 해석도 하지 않는다), 사설·루프백·링크 로컬 주소로 풀리면 거절한다(선언한 호스트 자체가 그런 주소 글자이면 그 주소만 허용). 판정마다 서버 실행기 출력에 한 줄 남기고 거절 수를 `egress_refused`로 보고해 0보다 크면 경보 `endpoint_egress_refused`가 열린다. 서버는 `HTTP_PROXY`·`HTTPS_PROXY`·`ALL_PROXY`로 중계를 쓰며, 프록시 환경 변수를 무시하는 클라이언트는 격리 안에 네트워크가 없어 어디에도 닿지 못한다(닫힌 채로 실패). 한계: 허용한 호스트 안의 내용은 보지 않고(CONNECT는 암호화된 채 통과), HTTP·HTTPS가 아닌 프로토콜(UDP·임의 TCP)은 쓸 수 없으며, 허용한 호스트가 다른 목적지로 전달하는 것은 막지 못한다. 격리를 쓸 수 없는 단말·사용자 수준 설치는 이 거름이 적용되지 않으며 Windows는 아래 AppContainer 항목과 같다. 그 밖에 `none`·`any`는 전부 막거나 여는 것이다. 계약의 주소·패키지 실행기는 등록할 때 보이는 단서일 뿐 집행 조건이 아니다. 패키지 실행기(`npx`·`npm exec`·`pnpm dlx`·`bunx`·`uvx`·`uv tool run`·`pipx run`)의 캐시 폴더(`~/.npm`, `~/.cache/uv`, `~/.local/share/pipx` 등)는 자동으로 읽기·쓰기로 붙고 홈의 다른 것은 붙지 않는다. 한계: bubblewrap이 없거나 사용자 이름공간이 막힌 단말에서 관리형 설치는 서버를 시작하지 않고(종료 코드 126, 설치 묶음 설정 `allow_unsandboxed`를 켠 경우만 격리 없이 시작하며, 관리형 설치 프로그램은 bubblewrap이 없으면 설치를 시도하고 못 하면 멈춘다) 사용자 수준 설치는 격리 없이 시작하며, 격리 없이 돌면 보고의 `sandbox` 값이 `none`이고 관리형이면 경보 `endpoint_unsandboxed`가 열린다. Windows 관리형 설치도 서버 실행기가 서버를 AppContainer(기능 없는 낮은 무결성 토큰) 안에서 시작한다(POL-O-13·POL-I-08, 조건부). 서버를 시작할 때마다 임시 AppContainer 프로필을 만들고, 그 SID에 선언한 경로(읽기 또는 수정), 실행 파일 폴더·스크립트 폴더·작업 디렉터리(읽기), 패키지 실행기 캐시(수정)의 접근 권한만 더한 뒤 시작하며 서버가 끝나면 권한과 프로필을 지운다(실행기가 비정상 종료해 남은 것은 다음 시작 때 기록을 보고 지운다). 서버는 작업 개체에 들어가 실행기가 끝나면 함께 끝난다. 선언하지 않은 사용자 폴더의 파일은 읽을 수 없고 읽기로 선언한 경로에는 쓸 수 없다. Windows·Program Files 폴더의 기본 읽기 권한은 막지 않는다. 네트워크는 `network: none`이면 기능이 없어 막히고, 선언이 없거나 `any`이면 인터넷·사설망 클라이언트 기능을 준다. `network: hosts`는 호스트별 거름을 집행하지 못한다. AppContainer는 서버 실행기의 루프백 중계에 닿지 못하고 주소별 거름 수단이 없으므로, 사설망 기능 없이 인터넷 클라이언트 기능만 주어 서버는 인터넷 전체에 접속할 수 있다. 이 경우 실행 기록·보고·서버 실행기 출력(`mint-egress unfiltered`)에 `egress_unfiltered`를 남기고 경보 `endpoint_egress_unfiltered`가 열려 호스트 제한이 집행되지 않음을 알린다. 호스트 제한이 필요한 서버는 Linux에서 실행하거나 `network: none`으로 선언한다. 관리자 계정 보고기는 사용자 프로필의 기록을 읽지 않고 실행 계약도 모르므로 이 값을 보고하지 못한다. 대신 제어 평면이 계약으로 판정한다. 승인 계약이 `network: hosts`인 서버가 `appcontainer`로 실행 중이라고 보고되면 보고에 플래그가 없어도 경보 `endpoint_egress_unfiltered`를 연다. 한계: AppContainer는 같은 단말의 루프백 수신기에 기본으로 닿지 못하고 이 실행기는 시스템 설정(루프백 예외)을 바꾸지 않으므로 `any`여도 로컬 수신기는 막히며, 주소별 거름은 없다. 격리를 만들지 못하면 관리형 설치는 서버를 시작하지 않고(종료 코드 126, `allow_unsandboxed`일 때만 격리 없이 시작), 사용자 수준 설치는 격리 없이 시작한다. 관리자 계정 Windows 보고기는 사용자 프로필의 실행 기록을 읽지 않는 대신(위 권한 모델) 운영체제에서 직접 판정한다. 실행기 프로세스의 자식(서버) 프로세스 토큰을 열어 AppContainer 여부와 그 SID가 실행기가 그 서버용으로 만든 프로필의 SID인지 확인하고, 맞으면 `appcontainer`, 아니면 `none`(그래서 `endpoint_unsandboxed`가 열린다), 토큰을 읽지 못하면 `unsupported`로 보고한다. 사용자 수준 Windows 보고기도 같은 토큰 값을 기록보다 우선한다(기록이 `appcontainer`여도 토큰이 아니면 `none`). 격리 상태는 단말의 주장이며, 실행 파일은 검증한 파일이 아니라 경로로 시작되어 검증과 시작 사이의 틈이 남는다. 관리자(root)로 도는 서버는 소유자가 다른 사용자인 파일을 격리 안에서 열 수 없다. 선언한 경로 안과 허용한 네트워크 안에서의 동작은 막지 않는다.
- 승인 서버 목록 반영과 단말 MCP 목록은 단말의 주장에 기대고 협조적인 단말에서만 정확하다. 보고 응답의 승인 서버 목록은 MINT가 만들지만 반영은 단말의 보고기가 하며, 관리형 보고기는 이 묶음이 쓴 계약 파일(기록한 해시와 같을 때)과 이 묶음의 실행기 항목만 고치고 같은 이름의 사용자 항목은 두므로 그 서버는 반영되지 않는다. 사용자 수준 설치는 반영하지 않는다. 단말 MCP 목록은 하네스 설정 파일에 적힌 항목만 보며(프로젝트의 `.mcp.json`, 설정 밖에서 뜬 서버, Python 3.11 미만의 단말에서 Codex 설정은 보지 못한다), 사용자가 보고기를 끄거나 설정을 숨기면 비어 보인다. Windows SYSTEM 보고기는 사용자 프로필을 읽지 않아 이 목록을 보내지 않으며, 마지막으로 받은 목록이 그대로 남는다. 목록은 자격 증명이 있을 자리를 읽지 않고 실행 파일 이름·호스트만 보내지만, 그 값 자체가 사실임은 확인하지 못한다.
- 승인은 90일(`MINT_RECERT_DAYS`)마다 관리자가 콘솔에서 「재확인」해야 하고, 요청 뒤 14일(`MINT_RECERT_GRACE_DAYS`) 안에 확인이 없으면 보류되어 그 범위의 호출이 `APPROVAL_RECERT_REQUIRED`로 차단된다(POL-O-14). 재확인은 승인이 아직 필요하다는 관리자의 확인을 기록할 뿐 필요성을 MINT가 판단하지 않으며, 서버 쪽 실행 권한과 인증 범위(OAuth 범위·계정 권한)의 실제 크기는 비교하지 않는다. 보류는 MINT의 판정에서만 효력이 있고 LiteLLM의 키·팀 권한은 그대로 남는다.

## 10. 복원·동기화·종료 판정의 보장 범위

아래 기능은 다음 범위로 보장한다.

- **복원.** 데이터베이스를 복원한 뒤 보장되는 것은 외부 저장소에 마지막으로 전송에 성공한 시점까지의 부정 상태(철회, 거부, 중지, 종료, 운영자 삭제·강등)뿐이다. 그 이후의 변경은 어떤 자료로도 복구를 증명할 수 없으므로, 작업 실행기는 되돌림을 판정하면 외부 쓰기를 멈추고 운영자가 `restore check`로 차이를 확인한 뒤 `restore attest`(또는 파일이 없을 때 admin 2인의 `restore accept-stale`)로 복원 요청을 남기기 전까지 차단을 유지한다. 시간 임계값은 판별 기준이 아니라 자료가 오래되었음을 알리는 경보 기준이다.
- **되돌림 보호의 위협 범위.** 지키는 것은 데이터베이스 되돌림(백업 복원, 시점 복구, 운영 실수)과 `mint_control`보다 낮은 권한(플러그인, 직원 화면, 그 밖의 역할)이다. `mint_control` 권한으로 원장 사건을 직접 위조하거나 콘솔 프로세스를 장악한 공격자는 범위 밖이다. 그 권한은 승인 자체를 할 수 있고 데이터베이스 안에서 위조 사건과 정당한 사건을 구별할 서명이 없으므로, admin 2인 확인도 이 권한의 침해에 대한 독립 방어가 아니다. 봉인 배치는 내보내기 키로 서명되므로 키를 모르는 쪽이 DB 안에서 연쇄를 다시 계산해 바꾸면 `seal verify`가 잡지만, 아직 봉인되지 않은 최근 사건(수 초~1분)과 키를 가진 쪽의 위조는 막지 못한다. 서명 도입 전 배치는 서명 없이 남는다.
- **LiteLLM 권한 동기화.** 수렴은 상한 보장이 아니라 목표이다. 정상 조건에서 원하는 상태로 수렴하는 데 한 번의 재조회 주기에 LiteLLM 권한 캐시 TTL(기본 60초)을 더한 시간을 목표로 한다. 측정은 MINT 상태 변경 커밋 시각에서 시작하고, 관리 API를 쓸 수 있는 구간만 센다. 수렴은 적용 뒤 읽기 확인이 원하는 상태와 일치한 시각이다. 늦게 완료된 외부 쓰기는 막을 수 없고, 재조회에서 교정이 연속 3회 실패하면 `sync_divergence` 경보가 발생한다. 자동 중지는 하지 않는다.
- **종료 판정.** 등급은 T0(미회수 또는 접근 지속), T1(종료 확인), T2(부분 종료), T3(증거 부족으로 판정 불가)이다. 종료 대상마다 다음 순서로 평가한다. (1) 회수 대상 하위 자격의 고지 또는 기관의 확인 수단을 충족하지 못하면 즉시 T3, (2) 회수되지 않았거나 접근이 지속된다는 증거가 있으면 T0, (3) 조치가 끝났으나 관측 구간이 지나지 않았으면 미판정, (4) 관측 구간이 지나고 차단 증거가 있으면 T1. 실패 판정은 관측 대기와 무관하게 즉시 내리며, 미판정 대상이 남아 있는 동안은 종합 T1을 내리지 않는다. LiteLLM의 세션·저장 자격 삭제는 업스트림 토큰 폐기를 의미하지 않으므로 그 자체로 차단 증거가 아니다.

## 11. 백업과 복원

`./mint.sh backup`은 데이터베이스 두 개, 정책 번들, LiteLLM 설정을 한 폴더에 모은다. 백업 폴더를 되돌리는 스크립트는 제공하지 않는다(데이터베이스 되돌림 뒤의 확인 절차는 `restore` 명령). 데이터베이스만 되돌리면 데이터베이스의 활성 정책 판본과 정책 엔진이 적재한 번들이 어긋나 판정이 판본 불일치로 차단되고, 설정만 되돌리면 통제 서버 구성이 어긋나므로 세 가지를 같은 시점으로 맞추는 대조가 필요하다.

## 12. 알려진 한계

- **대량 추출 탐지.** 결과량(바이트·항목 수)을 호출한 쪽·서버별로 지난 7일 평균과 견주는 통계 경보이다. 결과 크기를 보고하지 않는 경로(크기를 알 수 없는 응답)의 양은 세지 못하고, 평균 아래로 천천히 모으는 추출이나 처음부터 큰 사용은 바닥값과 배수 안에서만 잡힌다. 기본은 경보만 열며, `MINT_BULK_EXTRACTION_ACTION=hold`로 해당 호출한 쪽·서버의 호출을 거부로 막을 수 있지만 막기 전에 받아 간 결과는 되돌리지 못한다.
- **계약 위험 등급과 호출별 승인.** 고위험 도구의 호출별 승인 의무는 설정의 고위험 도구 목록과 선택된 승인의 조건에서 온다. 수용검증과 콘솔 승인은 도구 계약의 위험 등급으로 조건을 채우지만, 명령 도구의 `approval create`는 운영자가 준 고위험 도구 목록을 그대로 쓴다. 이 목록을 빠뜨리면 계약 등급이 높은 도구도 호출별 승인 없이 허용될 수 있다. 재승인으로 등급이 높아져도 기존 승인의 조건은 바뀌지 않는다. 설정의 고위험 도구 목록은 승인 경로와 무관하게 적용되므로, 반드시 호출별 승인을 받아야 하는 도구는 그 목록에도 넣는다.
- **기간을 고른 호출별 승인.** 10분·30분 승인은 같은 결속의 호출을 기간이 끝날 때까지 몇 번이든 허용하며 횟수 상한이 없다. 호출마다 사용 기록과 판정 사건이 남지만 기간 안의 반복은 사람이 다시 보지 않는다. 취소는 다음 호출부터 즉시 듣고, 이미 판정을 마친 호출은 되돌리지 않는다. 판정 프로세스의 시계가 아니라 데이터베이스 시계로 기간을 판정하며, 소비 때 결속이 하나라도 달라졌으면 사용 기록 없이 호출이 막힌다.
- **계약 교체 뒤 호출별 승인.** 호출별 승인은 도구 계약 판본에 묶이지 않는다. 재승인으로 도구 계약이 바뀐 뒤에도, 바뀌기 전에 받아 두고 아직 쓰지 않은 호출별 승인이 만료 전까지 같은 주체·도구·인자·정책 판본의 호출에 쓰일 수 있다. 계약을 바꿀 때 남은 호출별 승인을 철회하면 이 구간이 없어진다.
- **승인 조건의 기본값.** 승인에 적히지 않은 집행 조건은 MINT가 정책 입력을 만들 때 채운다(저장된 승인은 바뀌지 않는다). 허용 인자 키는 승인된 도구 계약의 입력 정의에 있는 이름, 삭제·외부 전송 도구는 항상 본인 확인 대상, `confidential`·`restricted` 자료 서버는 이용 목적의 동의가 기본이다. 허용 경로가 없으면 절대 경로는 모두 허용 범위 밖이다. 입력 정의에 없는 이름을 정상적으로 받는 도구는 승인에 허용 인자 키를 직접 적어야 하고, 도구 계약의 입력 정의를 읽지 못하면 이 기본값은 채우지 않는다.
- **허용 호스트의 합성.** 승인 조건의 허용 호스트와 조직·공통 외부 접속 대상은 합쳐서 판정한다. 승인 하나만 특정 호스트로 좁히려 해도 공통 목록에 있는 호스트는 허용된다. 이 검사는 인자 안의 주소 문자열을 보는 것이며 이름 해석이나 네트워크 접속을 막는 통제가 아니다.
- **패키지 취약점 조회의 범위(POL-O-06·O-07·O-08).** 버전이 고정된 npm·PyPI 패키지와 그것이 끌고 오는 의존 패키지(전이 의존성)를 조회한다. 의존 목록은 deps.dev 형식 API(`MINT_DEPS_GRAPH_URL`, 기본 공개 deps.dev, 비우면 끔)로 하루에 한 번 받으며, 의존 패키지의 취약점 경보에는 서버와 경로(`A → B`)가 적히고 치명이면 48시간 기한과 차단도 같다. 의존 목록을 받지 못하면 경보 `dep_graph_unreachable`만 열고 알고 있는 목록으로 이어 가며 호출은 막지 않는다(처음부터 받지 못한 패키지는 의존 패키지가 조회되지 않는다). 조회처가 모르는 패키지는 의존이 없는 것으로 본다. 컨테이너 이미지는 조회할 공개 API가 없어 취약점을 조회하지 않으며, 버전이 고정되지 않은 패키지·셸 스크립트 안의 설치·원격 서버도 조회 대상이 아니다. 번들된(복사해 넣은) 의존과 조회처가 해석하지 못한 의존은 보이지 않는다.
