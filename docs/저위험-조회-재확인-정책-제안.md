# 승인된 저위험 조회의 재확인 생략 제안

상태: 검토 제안. 이 문서는 현재 동작을 설명하는 운영 지침이 아니며, 실행 코드·OPA 번들·DB·기존 승인 기록은 변경하지 않는다.

## 문제와 목표

PJ3의 PJ5 합성자료 조회 시험에서 서버 도입 승인과 사용자 접근 승인을 완료한 뒤에도 호출별 관리자 승인과 요청자 본인 확인을 차례로 수행하고 요청을 재시도해야 했다. 서버 도입 승인, 사용자 접근 권한, 호출별 실행 확인은 서로 다른 절차이지만, 이미 검토한 범위의 저위험 조회에 동일한 확인을 반복하면 업무 흐름이 끊긴다.

다음 기준을 Policy as Code와 호출 전 확인 흐름에 반영하는 것을 제안한다.

> 서버 도입 검증과 필요한 관리자 승인·본인 확인을 완료했다면, 승인 유효기간 안에서 같은 사용자·서버·도구·목적지 범위의 저위험 조회는 재확인 없이 허용한다.

여기서 본인 확인은 요청자의 해당 사용 범위에 대한 확인이며, 서버 신청자의 확인을 모든 사용자에게 재사용하는 것을 뜻하지 않는다. 서버 도입 승인만으로 사용자별 도구 접근 권한을 새로 발급하지 않는다.

## 재확인 생략 조건

다음 조건을 모두 만족한 호출에만 적용한다.

- 서버 도입 검증과 승인이 유효하고, 현재 도구 계약이 승인본과 일치한다.
- 인증된 동일 사용자가 해당 서버·도구·목적지 범위의 유효한 사용 승인을 갖는다. 사용자 식별자는 프롬프트나 호출 인자의 자칭 ID로 대체하지 않는다.
- 해당 범위에 필요한 관리자 승인과 요청자 본인 확인의 완료 근거가 기록돼 있다. 확인 근거를 찾지 못하면 생략하지 않는다.
- 승인된 계약과 위험 평가에서 저위험 읽기로 판정된다. 도구의 `readOnly` 표기나 서버 이름만으로 저위험이라고 간주하지 않는다.
- 실제 인자가 승인된 목적지와 허용 작업 범위 안에 있다. 목적지는 기존 호스트·포트·경로 등 승인 조건을 적용하며, 리디렉션·주소 해석 후에도 목적지 검사와 내부 주소 보호를 유지한다.
- 모든 관련 승인·확인 근거가 만료·철회·보류되지 않았다. 적용 기간은 관련 근거의 가장 이른 만료를 넘지 않는다.

위 조건을 충족하면 반복 조회에서 새 호출별 관리자 승인 요청과 새 본인 확인 요청을 생성하지 않는다. 매 호출의 인증, 권한, 인자, 목적지, 계약 변경, 결과 검사 및 감사 기록은 계속 수행한다. 기존 정책의 명시적 거절이나 차단보다 우선하는 허용 규칙으로 만들지 않는다.

새 정책 도입 전의 1회 승인이나 다른 범위의 동의를 자동으로 기간 승인으로 바꾸지 않는다. 재사용 가능한 확인 기록의 범위·유효기간을 명시하고, 필요한 경우 최초 한 번 새로 확인한다.

## 다시 확인하거나 차단해야 하는 경우

| 변경 또는 상태 | 처리 기준 |
|---|---|
| 동일 사용자·서버·도구·목적지 범위의 저위험 반복 조회 | 유효한 근거로 재확인 생략, 호출 검사·로그 유지 |
| 다른 사용자 또는 승인 밖 도구·목적지 | 기존 정책대로 새 권한·확인 절차 또는 차단 |
| 도구 설명·스키마·계약 또는 위험 등급 변경 | 기존 재검증·재승인 절차 적용 |
| 승인·확인 만료, 철회, 보류 | 재사용 중단, 기존 정책 적용 |
| 업로드·삭제·명령 실행·자격정보 접근·외부 전송 등 | 이 제안의 생략 대상에서 제외, 기존 보호 유지 |
| 위험 등급·목적지·확인 근거 판별 불가 | 재확인 생략 금지 |

브라우저 서버 전체를 예외 처리하거나 모든 탐색을 읽기로 재분류하지 않는다. URL 조회도 인자에 비밀정보를 넣어 전송하거나 쓰기 동작을 유발할 수 있으므로, 검증된 읽기 작업과 대상에만 적용한다.

## 구현 시 검토할 지점

- `policy/bundle/mint/policy.rego`: 저위험 조회의 승인 재사용 조건과 기존 차단 규칙의 우선순위.
- `src/mint_litellm/plugin/pipeline.py` 및 `plugin/policy/defaults.py`: 호출별 관리자 승인과 요청자 확인의 적용 조건, 기본 보호와의 일관성.
- `src/mint_litellm/control/`: 사용자·서버·도구·목적지·계약·유효기간에 결속된 확인 근거와 철회 처리. 기존 상시 승인 규칙과 중복되거나 충돌하지 않는지 검토한다.
- 관리자·직원 화면: 재사용 범위와 만료를 보여 주고, 승인 없이 전체 서버가 열리는 것으로 오해하지 않도록 안내한다.
- 감사 기록: 재확인 생략 여부와 적용한 승인·확인 근거 식별자를 남겨 관리자가 추적할 수 있게 한다. 인자 원문·비밀정보를 추가 수집하지 않는다.

재확인을 전역으로 끄거나 Rego의 허용 판정만 바꿔서는 충분하지 않다. Python의 확인 단계와 정책 판정이 같은 조건을 사용해야 하며, 갱신·철회가 다음 호출에 반영되는지도 검증해야 한다.

## 수용 기준

1. 필요한 최초 관리자 승인과 요청자 확인이 없으면 기존 절차가 적용된다.
2. 두 확인을 완료한 동일 범위의 저위험 반복 조회는 새 확인 요청 없이 성공한다.
3. 다른 사용자·도구·목적지와 승인 경계를 넘는 인자는 재사용으로 허용되지 않는다.
4. 만료·철회·보류·계약 변경 이후 다음 호출부터 재사용이 중단된다.
5. 고위험 작업과 명시적 정책 차단은 영향을 받지 않는다. 분류·확인 근거가 없으면 생략하지 않는다.
6. 반복 조회에도 MINT 판정·감사 기록과 승인 근거가 남는다. MINT를 우회하는 직접 접속 경로를 추가하지 않는다.
7. OPA 정책 검사와 Python 호출 전 승인·확인 검사 양쪽에서 위 동작을 검증한다.
8. PJ3→LiteLLM/MINT→PJ4→PJ5 합성자료 조회로 정상·차단 사례를 검증한다. Wazuh 기록은 실제 감시 대상 네트워크 요청과 탐지 규칙이 있을 때 대조하며, 승인만으로 탐지 경보가 생긴다고 간주하지 않는다.

## 이번 제안의 범위 밖

`browser_snapshot` 노출·권한 연결과 PJ5 자료 URL 안내는 별도 작업이다. 이 문서는 정책 재확인 기준만 다루며, 본문 추출 기능 추가나 실행 중인 VM 설정 변경을 포함하지 않는다.
