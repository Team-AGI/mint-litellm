# 결정 기록

형식: `D-nnn · 결정 · 이유 · 영향`. 바꾸려면 새 결정을 추가하고 옛 결정에 「대체됨: D-nnn」을 적는다.

## D-001 · 기준 문서의 정본은 이 저장소의 docs/product다
- 이유: 기능 목록과 지시가 작업 중에 빠지던 원인은 작업자마다 다른 문서를 보았기 때문이다. 코드와 같은 커밋에서 바뀌어야 어긋나지 않는다.
- 영향: 구글 시트 「MINT for LiteLLM 기능·사용자 시나리오·버튼 매핑」은 보기용 사본이다. 시트에서 고친 내용은 이 폴더에 옮긴 뒤에야 유효하다.

## D-002 · 상태는 증거 기준으로 다시 매긴다
- 이유: 이전 「기기 실측 통과」는 구현자가 터미널·HTTP로 확인한 것이 많다. 독립 검증자의 실제 화면 조작 증거가 아니다.
- 영향: 이전 실측은 `BACKEND_VERIFIED`까지만 인정한다. `GUI_VERIFIED` 이상은 독립 QA 시험 ID(`QA-…`)가 있어야 한다. `scripts/product/check.py`가 이를 검사한다.

## D-003 · 작업자 역할
- 설계·UX 검토: Claude Mythos 5.2(소유자 지시로 Fable 대신)
- 구현: Claude Sonnet 5.5(범위가 정해진 독립 모듈), Claude Opus 5.5(핵심·난제·통합)
- 독립 검증: GPT-6.2 Sol(Codex). 구현자가 아닌 쪽이 실제 화면과 하네스를 조작한다.
- 최종 판정: Opus 5.5. 다른 모델의 결과는 근거와 실제 동작으로 확인한 뒤 반영한다.
- 각 작업자는 끝날 때 TASK_ID·MODEL·BASELINE_COMMIT·CONTROL_SHEET_REVISION과 10개 항목 보고를 돌려준다.

## D-004 · LiteLLM 자체 MCP 기능은 실제 판본에서 확인한 뒤에만 재사용한다
- 이유: 문서에 있는 기능이 운영 판본(1.106.x)에 같은 형태로 있다는 보장이 없다. 이전에도 읽기 응답이 `mcp_info`를 지워 신청 판별이 깨진 적이 있다.
- 영향: 제출(submissions)·통제(mcp_control)·접근 그룹 재사용 여부는 조사 결과를 이 기록에 덧붙여 정한다.

## D-005 · 저장소에는 IP 주소, 자격 증명, 키, 개인 계정명을 적지 않는다
- 시험 장비는 「기기」「Linux PC」「Windows PC」로 적는다. 화면 캡처 같은 증거 원본은 저장소 밖에 두고 시험 ID로 찾는다.

## D-006 · 지킬 설계 결정은 PRODUCT_BRIEF 「지킬 설계 결정」 7개다
- 소유자가 확정한 원칙(승인 한 번, 도구 기본 통과와 사후 차단, 입력 최소, root 단독 결정, 가용성 우선)이다. 재설계 제안이 이와 부딪히면 CHANGE_PROPOSALS로 올리고 소유자 확인 전에는 구현하지 않는다.

### D-004 조사 결과 (PC-LLM-01, LiteLLM 1.106.6 실제 판본 확인)
상세는 `LITELLM_MCP_REUSE.md`. 제출(submissions)·서버 등록·승인·거절·서버 단위 키·팀 `mcp_servers` 권한·`pre_mcp_call` 가드레일·사용자별 자격 삭제는 1.106.6에 있고 MINT가 이미 쓴다(유지). LiteLLM 도구 권한(`mcp_tool_permissions`)은 허용 목록뿐이고 `blocked_tools`·서버 `disallowed_tools`는 MCP 경로에서 쓸 수 없으므로(후자는 config 전용) 「새 도구도 기본 통과, 사후 차단」은 MINT 플러그인이 계속 맡는다. 접근 그룹·toolset·서버 `DELETE`·`DELETE /v1/mcp/sessions`(요청받은 워커 하나에만 적용)는 쓰지 않는다. LiteLLM에는 서버 비활성 플래그와 전역 MCP 정지 설정이 없으며, 활성 서버에 대한 `reject`가 즉시 비활성화(재승인으로 복구, 요청마다 DB 개정 번호로 전파)이므로 root 즉시 중지·이용 종료에 보조 수단으로 추가할 것을 권고한다(소유자 확인 불필요: 결정 3·4와 충돌 없음, 구현은 별도 작업). 키·팀·권한 캐시는 기본 60초(`user_api_key_cache_ttl`)이고 Redis 방송은 최선 노력이라 LiteLLM 쪽 폐기 반영은 최대 60초 이상을 가정해야 하며(FM-59), 즉시성은 MINT 판정이 맡는다. LiteLLM은 서버 등록·수정·삭제의 감사 로그를 남기지 않아 MINT 원장이 유일한 근거다. 읽기 전용 조사라 `reject` 직후 다른 워커의 세션 차단·`rpm: 0` 집행·키 차단 즉시 전파는 미재현이다.
